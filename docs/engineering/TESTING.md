# Testing Strategy

How we test Fivvi so that AI agents and humans can change it often without breaking it. The tools are fixed by ADR-014 (`ROADMAP.md §4`). This document covers **what** to test, **where**, **how**, and **what blocks a merge**. It applies to every PR.

## 1. Principles

1. **Tests ship with the change.** A PR that adds or changes behaviour includes the tests for it. "Tests later" does not exist, just like "translate later".
2. **Acceptance criteria become tests.** Every acceptance criterion in a spec issue maps to at least one automated test (§6). If a criterion can't be automated, the spec says why and how it is checked by hand.
3. **Bug fix = failing test first.** Reproduce the bug in a test, see it fail, then fix it. The test stays as a regression guard.
4. **Test at the lowest layer that can prove the rule.** Business rules live in `packages/domain`, so most tests live there too. E2E tests prove that the pieces are wired together; they don't re-test every rule.
5. **Real Postgres, not mocks, for data.** RLS, constraints, transactions and locks are part of our correctness. Mock only at system boundaries (§5.4).
6. **Deterministic or it doesn't count.** No real clock, no real network, no `sleep`. A flaky test is a bug (§8).
7. **Never weaken a test to get green.** Don't delete, skip or loosen assertions, and don't update snapshots without reading the diff. If a test is wrong, fix it in the PR and explain why in the description.

## 2. Test layers

| Layer | Tool | Lives in | Proves | Speed |
|---|---|---|---|---|
| **Domain unit** | Vitest | `packages/domain/**/*.test.ts` (next to the code) | Business rules: recurrence, capacity, holds, permissions matrix, time and locale formatting | ms, no I/O |
| **API integration** | Vitest + real Postgres | `packages/api/test/**/*.integration.test.ts` | Routes end to end in-process: validation, auth, roles, tenant scoping, RLS, transactions, migrations, response matches the OpenAPI schema | seconds |
| **Tenant isolation suite** (E011) | Vitest + real Postgres | `packages/api/test/isolation/*.integration.test.ts` | Workspace A can never read or write workspace B's data, through **any** route (§4.1) | seconds |
| **Email** | Vitest | `packages/email/**/*.test.ts` | Every template renders in nl-NL and en with no missing keys; links and dates are correct | ms |
| **Web component** | Vitest + Testing Library | `apps/web/**/*.test.tsx` | Only for components with real logic (forms, pickers, stateful widgets). Not for static markup | ms |
| **Web e2e** | Playwright | `apps/web/e2e/*.spec.ts` | Critical user flows in a real browser, **in NL and EN**, with axe accessibility checks; mobile viewport for public pages | minutes |
| **iOS unit** | XCTest | `apps/ios/FivviProTests/` | View models, state handling, API-client mapping, error states | seconds |
| **iOS UI** | XCUITest | `apps/ios/FivviProUITests/` | A few platform-specific flows Maestro can't cover | minutes |
| **Android unit** | JUnit | `apps/android/app/src/test/`, `apps/android/core/src/test/` | View models, state handling, API-client mapping, error states | seconds |
| **Android UI** | Compose UI tests | `apps/android/app/src/androidTest/` | Screen states and interactions | minutes |
| **Mobile e2e** | Maestro | `e2e/maestro/` | **The same flow YAML on iOS and Android**, in both locales. This is the parity acceptance test (M8, the native track: run per milestone from M2) | minutes |
| **Static checks** | CI (E002, E005, E018) | — | Lint, typecheck, i18n parity, ICU syntax, no hard-coded strings, OpenAPI drift, generated clients up to date | seconds |

The file name picks the suite: `*.test.ts(x)` is a unit test (`pnpm test`, no database), `*.integration.test.ts` an integration test (`pnpm test:integration`, real Postgres), and `apps/web/e2e/*.spec.ts` a Playwright spec (`pnpm test:e2e`). The shared Vitest presets in `packages/testing` (`unitConfig`, `integrationConfig`) apply this split, run tests with `TZ=UTC`, restore mocks, stubbed env and globals after every test, and turn retries off.

Rough shape: many domain tests, a solid layer of API integration tests, a small number of e2e flows. If an e2e test is the only thing catching a rule, add a lower-level test for that rule.

## 3. What to test, by type of change

Use this as the checklist when writing and reviewing a PR.

| Change | Required tests |
|---|---|
| New or changed **business rule** | Domain unit tests, including edge cases and invalid input |
| New or changed **API route** | Integration test: happy path, validation error, **every role** (Owner / Trainer / Client / anonymous) allowed or denied as specified, response matches the schema. The isolation suite picks the route up automatically (§4.1) |
| **Schema / migration** | Migrations apply to an empty DB and on top of the previous version; RLS policy exists for every new business table (a test checks this) |
| **New table** | Declared in the privacy registry (`packages/domain/src/privacy/registry.ts`) in the same PR, with its subject, personal-data columns, export columns and what deletion does; then `pnpm --filter @fivvi/domain generate:privacy` and commit `docs/engineering/PRIVACY.md`. A test fails naming a table that is missing, and another when the inventory is out of date (E014) |
| **Scheduling, time, recurrence** | DST fixtures (§4.3); times near midnight in Europe/Amsterdam |
| **Booking, capacity, holds** | Concurrency test (§4.2); hold expiry; cancellation frees the spot |
| **Tokens** (magic link, 6-digit code, invitations) | Single use, expiry, stored hashed, rate limit, wrong-workspace rejection |
| **Notes / health data** | Roles that must not see notes get a denial, and no note content leaks into lists, emails, logs or error messages |
| **User-facing web flow** | Playwright e2e in NL **and** EN for the flow's main path |
| **Mobile feature** | Unit tests on **both** iOS and Android for the view model, plus a Maestro flow (both locales) for the main path |
| **Strings** | Covered by CI checks; no extra test unless the string has plural or date logic |
| **Email template** | Render test in both locales |
| **Bug fix** | A regression test that fails without the fix, at the lowest layer that reproduces it |
| **Refactor, no behaviour change** | Existing tests stay green, unchanged. If you have to change tests, it wasn't a pure refactor |

## 4. High-risk areas

These are the bugs that hurt most (`ROADMAP.md §13`: R2, R3, R4). They get dedicated, always-on tests.

### 4.1 Tenant isolation (R4)

- The suite **enumerates every route from `openapi.json`**. For each route that touches a business record it creates data in workspace A and calls the route as a user of workspace B. Expected result: `404` (never `403`, so we don't reveal the record exists) and no data from A in the response.
- A new route without an isolation case fails CI. Public routes are listed explicitly in an allow-list, which is reviewed in the PR.
- **The sweep tests have a 180 s timeout, not Vitest's 30 s.** A test that runs the whole sweep (`runIsolationSuite`: every route as every actor, about 700 calls of 7 to 9 round trips each, plus a read of every table after each call) takes 5 to 10 s on an idle machine, and 25 to 35 s with the load average at 60 to 80 (several agents building at once); 67 s was seen once. The cause is the machine waiting for CPU on every round trip, not the code, and the 30 s default then failed `scripts/check.sh` on `main` and on branches alike (#678). Those tests pass `SWEEP_TIMEOUT_MS` (`packages/api/test/isolation/harness.ts`) as their timeout, about 2.5 times the slowest run seen, so a sweep that hangs still fails. They test every route and every actor all the same: the timeout is the only thing that gives. The suite keeps its round trips few: one statement reads every table, it is a prepared statement planned once per connection, a call starts from the rows the last one left, and a world that only runs the sweep does not read the tenant context back on every request (`createWorld({ observe: false })`). Do not raise the timeout of any other test for a busy machine; speed the test up or ask first.
- A second set of tests runs queries directly against Postgres with a workspace-scoped role to prove RLS blocks cross-tenant reads **even if the data-access layer has a bug**.

### 4.2 Overbooking (R3)

- Fire N parallel booking requests (separate DB connections) at an occurrence with 1 spot left. Exactly one succeeds; the others get a "full" result; the database agrees.
- The same for holds: an active hold counts against capacity; an expired hold does not.

### 4.3 Time and daylight saving (R2)

- Fixed fixtures for the **last Sunday of March and October** in Europe/Amsterdam: "every Tuesday 18:00" stays 18:00 local on both sides of the change.
- Times between 00:00 and 02:00 local, which fall on the previous day in UTC.
- Rendering: nl-NL `22 september 2026`, `18:00`; en uses the English format, same timezone.

## 5. Conventions

### 5.1 Naming and traceability

- Group tests by feature ID and name them after the behaviour, not the function:
  `describe('F029 booking hold')` → `it('releases the spot when the hold expires')`
- Tests that cover an acceptance criterion reference it: `it('AC2: client receives the confirmation email in their locale')`. A reviewer can then check the spec issue against the test list.
- Native: the same idea in XCTest/JUnit method names, e.g. `test_F043_AC1_logsSetWhileOffline`.

### 5.2 Test data

- **Factories, not fixtures files.** Shared builders will live in `packages/testing` once the first business tables exist (M2), e.g. `createWorkspace()`, `createTrainer(ws)`, `createClass(ws, { capacity: 1 })`. They create valid records with sensible defaults, so a test only states what matters to it.
- **Every test creates its own workspace.** Tests never depend on each other's data or on order, and they can run in parallel. This also exercises tenant scoping by default.
- **Seed data is for local development and the e2e baseline only.** Tests don't modify shared seed data.
- **No real personal data**, ever. Use obviously fake names and `@example.com` addresses.
- **Secrets in tests are obviously fake**: low-entropy and self-describing (`fake-link-token-for-tests`, `fake-api-key-for-tests-only`), never a realistic random-looking token or key and never one assembled from parts. Only a test whose fixture has to match a scanner's pattern (a scanner's own tests, or a key header the script under test checks) may split the prefix that pattern matches; the rest stays obviously fake. A realistic fixture trips the secret scanner (GitGuardian) and hides a real key pasted into a test. `scripts/check.sh` runs `scripts/secrets-in-tests.mjs`, which fails on one; its header says what it looks for, and a fixture that has to stay realistic goes in `scripts/secrets-allowlist.txt` with a reason.

### 5.3 Database

- Local: Postgres in Docker (`pnpm db:up`, same major version as production). CI: a `postgres:18-alpine` service container in `Checks (Linux)` and in `E2E (Linux)`, where the e2e servers create their own databases. Never run tests against the Railway production or preview databases: the helpers refuse any server that isn't on `localhost`.
- Tests never share data. `@fivvi/testing/database` isolates them at three levels:

| Level | How | Helper |
|---|---|---|
| **Run** | The package's Vitest global setup creates a **template database** and applies the migrations once. Nobody may connect to it afterwards. Teardown drops the template and every database the run created | `setupTemplateDatabase(migrate)` from `@fivvi/testing/database/setup`, in `test/global-setup.ts` |
| **Test file** | `beforeAll` clones the template into the file's own database (`CREATE DATABASE … TEMPLATE`, milliseconds, no migrations), `afterAll` drops it. Files run in parallel on different workers without seeing each other | `cloneTemplateDatabase()` |
| **Test** | The test body runs in one transaction that is **always rolled back**, so every test starts from the migrated, empty state | `withRollback(db, async (tx) => …)` |

- **Transaction rollback is the default** for API integration tests and the E011 isolation suite. It fits the RLS model: the per-request context (`SET LOCAL ROLE`, `set_config('app.organization_id', …, true)`) is transaction-local, so a test sets it inside `withRollback` and it disappears with the rollback. For this to work, code under test takes the executor it runs on (`DatabaseExecutor`: the database or a transaction) instead of opening its own pool, and the in-process API gets its executor injected per request.
- **Commit instead** when rollback can't prove the behaviour: concurrency tests with separate connections (§4.2), anything a second connection must see, deferred constraints (checked only at commit), `now()` differences (it is the transaction's start time inside one transaction), and migrations. Such a test creates its own database, `cloneTemplateDatabase()` (migrated) or `createTestDatabase()` (empty, for migration tests), and drops it in `finally`.
- **Rejected: a schema per worker.** RLS policies, grants and the migrator's `drizzle` schema are schema-qualified, so `search_path` tricks would test a different setup than production. A database clone keeps the real schema names and is just as fast.
- **Roles are per server, not per database** (E011): create the app role, the cron role (E012) and the migration role idempotently in the global setup, before the template is migrated; a clone doesn't copy them.
- Concurrency tests use real, separate connections and are allowed to be slower.

### 5.4 Time, locale and external services

- **Clock:** domain code gets "now" from an injected `Clock` (`{ now(): Date }`), never `Date.now()` / `Date()` / `new Date()` directly. Tests use a fixed clock. The test process runs with `TZ=UTC` so the machine's timezone never leaks in. `@fivvi/testing/clock` has the helpers:
  - `fixedClock(instant)`, `manualClock(start)` with `advance({ hours: 25 })`, and `freezeSystemTime(instant)` for code that can't take a clock (it restores the real clock after the test);
  - `zonedTime('2026-03-31T18:00')` turns Europe/Amsterdam wall-clock time into an instant, and `wallTime(instant)` goes back. A time in the skipped or repeated DST hour throws unless the test passes `disambiguation` (`earlier`, `later`, `compatible`), so no test picks one by accident;
  - `dstTransitions(2026)` gives the §4.3 fixtures from the time zone database: the instant, local date, offsets and the skipped/repeated hour of the March and October changes.
- **Locale-independent selectors:** e2e and UI tests find elements by role + accessible name from the catalog, or by test ID / accessibility identifier, so **the same test runs in both locales**. Assert on visible text only where the text is the point, and read it from `packages/i18n`, never hard-code Dutch or English in a test.
- **Mock only at boundaries:** email provider (a capture transport that records to, locale, subject and links), Cloudflare Turnstile (official test keys), Sentry/PostHog (disabled without a DSN or key; to check what would be sent, use the capture transport of `packages/observability`, or for page views `scrubPageView()` and an e2e test that intercepts the PostHog host, [OBSERVABILITY.md](OBSERVABILITY.md) §5.2), the clock. Don't mock the database, the domain package or our own API.
- **No network** in unit and integration tests. E2E hits only our own local stack.

### 5.5 Coverage

- Coverage is reported on every PR, but **the checklist in §3 is the real bar**, not a number.
- One hard gate: `packages/domain` line coverage must not drop below **90%**. That package is small, pure and where the rules live, so it is cheap to keep high.

## 6. Test plan in the spec issue

Every spec issue (`docs/agents/issue-tracker.md`) has a **Test plan** in its *Testing Decisions*, written **before** implementation, at the seams `/to-spec` agreed with the owner. It lists each acceptance criterion with the layer(s) that prove it:

| AC | Layer | Test |
|---|---|---|
| AC1 (NL/EN) | Playwright | `apps/web/e2e/booking.spec.ts` → `AC1: client books a class` |
| AC2 | API integration | `packages/api/test/bookings.test.ts` → `AC2: rejects booking when full` |
| AC3 | Domain unit | `packages/domain/booking/hold.test.ts` → `AC3: hold expires after 10 minutes` |

The reviewer checks this table against the code.

## 7. Where tests run

| When | What runs |
|---|---|
| **Locally, before opening a PR** | `scripts/check.sh`: the checks the change can affect (`check.sh --all` runs everything; §7.1, [ADR-024](../decisions/ADR-024-run-only-the-checks-a-change-can-affect.md)). Agents paste the commands and results in the PR description. Mobile changes: build and run the unit tests and the affected Maestro flows on both platforms locally |
| **Every PR (Linux, required)** | `Checks (Linux)`: static checks, domain unit, API integration, isolation suite, email, web component; turbo skips a task whose inputs did not change, the integration tests included. `E2E (Linux)`: Playwright (NL + EN), when the web app or a package it depends on changed (skipped otherwise; a skipped required check passes) |
| **PR touching the Android app or its inputs (Linux, required when triggered)** | `Android`: `android.sh build`, `verify` and the Maestro flows, in parallel jobs (§7.1). Path-filtered; the paths are in `WORKFLOW.md §7` |
| **PR touching the iOS app or its inputs (macOS, required when triggered)** | `iOS`: one build, then the nl and en test passes as two parallel jobs (§7.1). Path-filtered to save macOS minutes (ROADMAP §12); the paths are in `WORKFLOW.md §7` |
| **PR touching mobile apps, contract or strings** | Maestro flows on the platforms affected. If CI minutes run short, Maestro runs locally and nightly instead; the PR description must say it ran |
| **Before a TestFlight / Play internal build** | Full suite on both platforms, both locales; the release run does it first and uploads nothing when a suite fails ([`RELEASE.md`](RELEASE.md)) |

**Budget:** keep the required Linux checks under ~10 minutes. If they get slower, speed them up (parallelise, move logic tests down a layer), don't drop them.

`TEST_DATABASE_URL` falls back to `DATABASE_URL`; `packages/database` also reads either from its git-ignored `.env`. Without one, integration tests fail with a message instead of being skipped. Tests only create and drop their own `fivvi_test_*` databases, so they don't disturb the dev database on the same server.

Inside a package, `pnpm exec vitest` watches unit tests, `pnpm exec vitest --config vitest.integration.config.ts` integration tests, and in `apps/web`, `pnpm exec playwright test --ui` debugs e2e specs (after `pnpm build` and `pnpm db:up`). Playwright writes `playwright-report/` and `test-results/` (git-ignored); CI uploads them when `E2E (Linux)` fails.

**Writing a Playwright spec:** import `test` and `expect` from `apps/web/e2e/fixtures.ts`. Each spec runs once per locale project (`nl-NL`, `en`); the browser language is set to the project's locale. The `messages` fixture is that locale's catalog, `otherLocale` the other one, for switching. Every test ends with an automatic axe check (WCAG 2.2 A and AA) on the page it left open; call `expectNoAxeViolations(page, 'the open dialog')` for states in between. Every test also fails on any `securitypolicyviolation` in the browser (the automatic `cspViolations` fixture, E013 AC9; it watches the contexts a test opens with `browser.newContext()` too); a test that provokes one on purpose reads and drains it with `cspViolations.drain()` (`apps/web/e2e/csp.spec.ts`). `apps/web/test/e2e-fixtures.test.ts` fails a spec that takes `test` from anywhere else.

**Budgets of the public website (F064 AC15, `apps/web/e2e/site-a11y.spec.ts`, `site-budgets.spec.ts`, `test/budgets.ts`):** two kinds of check, and they run in different places.

- **In CI on every PR (they are part of `pnpm test:e2e` and `scripts/check.sh`):** `site-a11y.spec.ts` runs axe with the WCAG 2.2 A and AA rules and the best practices (`SITE_AXE_TAGS`) on every site page, in light and dark, on a laptop and on a phone, each language project in its own language (so the two together cover both). The image checks are unit and e2e tests of the pages: every picture is a modern format (AVIF, WebP) in sizes of its own, with `width`, `height` and `sizes` set, the first miniature has a high fetch priority and the screens a low one, and every image on a page loads (`home-page.test.tsx`, `audience-page.test.tsx`, `site-home.spec.ts`, `site-audiences.spec.ts`).
- **Not in CI: the Lighthouse budgets,** `pnpm --filter @fivvi/web test:budgets`. They run against **the PR's Railway preview** for a PR that changes the site (the result is recorded on the PR as a comment: paste the table the run prints and writes to `apps/web/test-results/budgets-summary.md`), and against **production at go-live** (#648). They are not a gate because Lighthouse's *simulated* largest contentful paint on a shared CI runner is too noisy: the simulation takes timings from a trace of the real page load, those are sensitive to what else the 4-vCPU runner does at that moment, and the same page lands on 1.8 s in most runs and on 2.5 s or more in some (steps of about 150 ms, the simulated round trip). A gate with that spread either fails PRs that did nothing wrong or has its threshold loosened until it no longer protects the budget, and the CI job of the e2e tests has no minutes to spare for it (15 in all). A person runs it on a quiet machine, sees the numbers and the room left, and a run that is over budget is looked at, not retried until it passes.

`site-budgets.spec.ts` runs Lighthouse (the `lighthouse` dev dependency of `apps/web`, in Playwright's own Chromium) on the homepage and the four audience pages in light and dark, in both languages, on Lighthouse's phone profile (Moto G Power, slow 4G, simulated from a trace): the largest contentful paint must stay under 2.5 s, the layout shift under 0.1, SEO and accessibility must score 100, and no image may be unsized, oversized or in an old format. `pnpm test:budgets` is `E2E_BUDGETS=1 playwright test --workers=1`: the `budgets-nl-NL` and `budgets-en` projects replace the language projects (`playwright.config.ts` picks one set or the other), so `pnpm test:e2e` and `scripts/check.sh` do not run them. One worker, so only one Chrome measures at a time. A page that is over budget is measured up to three times and its best run counts; a Lighthouse run that takes over a minute fails with its address. **Against a deployed site** `BUDGETS_BASE_URL=<origin>` (it implies the budgets run) starts no web server and no database: the same go-live proxy sits in front of the address, so SEO is measured as at go-live, the same as locally; a value that is not an http(s) address is an error, never a silent local run, and a site whose `/api/v1/health` does not answer (a preview that is gone or still deploying) stops the run with that message. **The result** is one Markdown table for both languages, printed at the end of the run (`e2e/budgets-reporter.ts`) and written to `test-results/budgets-summary.md`: per page and colour scheme the LCP, CLS, SEO, accessibility and the verdict (which budget is over), and the host's `benchmarkIndex` and the CPU multiplier. The annotations of each test (`AC15 en dark /en/gyms`, in the HTML report and the JSON) carry the same numbers and the LCP of each run. **The CPU is calibrated to the host:** Lighthouse slows the CPU down relative to the machine it runs on (4x by default, which assumes a high-end desktop), so a slower host would emulate a slower phone. Before the runs the spec measures the host's `benchmarkIndex` with Lighthouse's own computation (median of three samples) and sets `throttling.cpuSlowdownMultiplier` with the formula of Lighthouse's CPU throttling calculator, which `docs/throttling.md` links to (`test/lighthouse-cpu.ts`, unit-tested): 1x at 150, 2x at 800, 3x at 1300, 4x at about 1530, never below 1x and never above 20x (the documented range); the network stays Lighthouse's slow 4G. The thresholds do not move with the host. (With a preview the host is the machine that runs Chrome, not the server.) **SEO is measured as production serves it:** the e2e servers and every preview say `noindex` in the `X-Robots-Tag` header and disallow everything in `robots.txt`, like every environment but production (the switch `siteIndexable` has been `true` since #648, so the markup of the site carries no `robots` tag anywhere), so a small proxy (`e2e/go-live-proxy.ts`) sits between Lighthouse and the site and shows what production sends: no `X-Robots-Tag`, the `robots.txt` that `robotsTxt` gives production, and the canonical URL pointing at itself. The spec first checks, with `robotsHeader`, that production would index the page, and a test compares the proxy's view with the site's, so only those differences exist. Against production itself no proxy is needed for the site, but the run still goes through it, which changes nothing. Production itself is a valid target: the comparison test recognises which of the two states the address is in from what it serves (`serverEnvironment` in `test/budgets.ts`: no header and the production `robots.txt`, or `noindex` and the disallow-all one) and asserts that state in full, so a mix of the two fails.

**Sign-in specs and the rate limits (F001 AC10, from #134):** sign-in requests are limited per IP address and per email address, so a spec that signs in uses its own `x-real-ip` and its own email address, never one shared with another spec, locale or retry. Which header, the limits and why: [ENVIRONMENTS.md §7](ENVIRONMENTS.md#7-variables) and the [auth README](../../packages/auth/README.md).

## 8. Flaky tests

- A flaky test is a bug with a priority, not noise. Fix the cause (usually a race, a real clock or shared data).
- CI retries are off for unit and integration tests, and for XCTest and the Compose tests (CI's iOS retry job, #1268, re-runs only a job that got no runner, never a failed test). Playwright and Maestro may retry once, and a test that only passes on retry is reported as flaky.
- **Locally the suite does not compete with itself** (#1336). With 4-6 factory builders each running its own `check.sh`, the machine's load average went to 20-45 and the heaviest tests failed in changes that leave `apps/web` alone: `theme.spec.ts` AC15 and AC7 timed out at Playwright's 30 s, the roles, site-search, clients and workspaces tests ran 2-8 times as long as alone, and `axe-settled.spec.ts` #287 failed on an axe violation after 2-4 s (cause below). Two things keep that out: the `check.sh`s queue for the suite (one suite at a time on the machine, see the `check.sh` row above; a suite that is a turbo cache hit does not wait) and a local run takes fewer workers when the machine is busy (`localWorkers` in `apps/web/test/e2e-run.ts`: half the cores when idle, down to 2 as the load takes the cores; CI keeps its 3). No timeout was raised, no test changed; a test that fails alone fails the run as before.
  - **Where the time goes** (trace of the heaviest tests, one worker): `page.evaluate` (axe and computed-style sweeps, animation settling) 55-60 % of the heaviest, navigations about 10 %, page creation about 8 %, nothing in the server (the production build, started before the first test): browser CPU. A CPU hog alone costs little (the tests below take 1-1.5 times as long next to 40 `yes` processes); what costs is other Chromiums: every worker of every suite runs a multi-process browser, so suites that start together oversubscribe the cores.
  - **Per test, seconds, nl-NL / en** (10 cores, 12 Nov 2026; line numbers of f441718f): *alone* is one worker at a load of 5.5; *1 worker, load 33-43* is the same with 28 `yes` processes added (best-worst of 3 runs); *loaded suite* is the whole suite on 5 workers (the old default) at a load of 48 rising to 154, other builders included (a failed test is marked **F**); *queued suite* is the whole suite through `check.sh` (2 workers, load 64-97) and passed 658 of 658.

With one worker it comes 200-320 ms after the fade began, even at a load of 150; with 10 workers on a load of 150 it came a median 1004 ms after (24 of 28 probes saw the fade already finished), the check then trusted axe's read of the half-faded button (about 1.4:1) and failed with `axe violations on a fade whose event has not come` (34 of 40 runs, 1.8-4.3 s). - **The iOS release retries a failed UI test once** (#1433). `release.sh tests ios <locale>` runs `scripts/test-ios.sh test <locale> --retry-failed`, the only caller that passes it. A run on `main` already passed CI in the merge queue, so a UI test that fails there and passes on the same tree is flaky by the rule above, and the release (about 50 minutes) should not be lost to it. When the run fails, the failed UI tests (`FivviProUITests`) run again once, on the same simulator, with `-only-testing:` for each, the same test-plan configuration and allowances, into `TestResults-<locale>-retry.xcresult`, within `IOS_RETRY_DEADLINE` (600 s, with the grace). The job passes only when every one of them ran and passed in the retry. **No retry** when a test that failed is not a UI test (unit tests are never retried), when more than 3 UI tests failed (a break, not a flake), when the first run hit its deadline (#305, a stall), when the failed tests can't be read from the result bundle, or when the first run is not shown to be complete: its summary's failed-test count must equal the failed tests the reader found, and its total (`totalTestCount`) must equal the number of tests its configuration has, which `xcodebuild test-without-building -enumerate-tests` counts first (about 20 s, `IOS_ENUMERATE_DEADLINE` 120 s), so a run that aborted for a reason that is no test (a lost connection to the test runner, a bundle that never started its tests) with one listed failure is not retried into a pass. A test that passed only on its retry is a `::warning::flaky:` annotation and a section of the job summary with its first failure message: file a bug for it and quarantine it as below (a test of the required jobs may sit in the quarantine for 7 days at most), so the retry doesn't hide it.
- **The web e2e suite keeps a fifth of its limit to spare on CI** (#1301, #1408). It runs on 3 workers, not Playwright's default of 2 on the 4 vCPU runner (the 650 tests added up to 1156 s of test time in a 594 s run on 2 workers, so those were saturated), and stops itself after 17 minutes, earlier than the job's own `timeout-minutes` (`apps/web/test/e2e-run.ts`; tests keep the gap to the job's limit and to the push run's step limit). The limit is a guard for a hung suite, not a budget: it keeps 20 % of itself to spare for `MEASURED_WORST_SUITE_MINUTES` (13.5, the slowest measured run scaled to the suite of the next main), and a test fails when the two disagree. A run that does hit it prints one `::error` annotation (`apps/web/e2e/timeout-reporter.ts`) saying the suite timed out, whether any test failed (a test that failed and whose retry was cut off counts as failed) and which tests were cut off.

- **Quarantine** ([ADR-025](../decisions/ADR-025-requeue-after-a-fix.md), amendment of 12 November 2026): a flaky test that removes a PR from the merge queue is quarantined first and fixed within the week. A quarantined test is moved, not skipped: it leaves the required jobs and keeps running.
  - **Evidence:** a test counts as flaky only when it failed and also passed on the same code, with both run ids in its bug: the same commit (a re-run of the failed job), or the same tree in a merge group and in a push or daily run on `main`. A test that fails every time is broken, not flaky; it is fixed, not quarantined. A cause that is not a test (a runner, a mirror, a timed-out job) is not quarantined either.
  - **Owner:** whoever is assigned the bug, and the factory while nobody is. The bug is for the real fix; a small quarantine ticket adds the test to the list.
  - **The list:** one file per test runner in `quarantine/` (`vitest.txt`, `playwright.txt`, `xctest.txt`, `compose.txt`, `maestro.txt`), outside every guardrail path (risk group `quarantine`, agent-queueable until pilot setup). One entry per line, `test | bug | added | end`: the full test name, the bug as `#1400`, and two dates as `YYYY-MM-DD`; the dates are UTC days, and the rule compares them with today's date in UTC. Lines that start with `#` are comments.
  - **The `Quarantine` job** (`WORKFLOW.md §7`): the required jobs leave the listed tests out, and this job, which is not required and never will be, runs exactly those tests on every CI run, so their results stay visible and the fix can show it works there. It passes while the lists are empty, and then only reads them. **It never fails, also when a listed test does:** a red check would hold back the merge gate, `pr.sh ready`, `flow.sh` and the Railway preview, which wait on every check, and the quarantine exists to unblock them. A listed test that fails is in the job summary (per runner: the failed tests, or that all passed) and in one `::warning` annotation per runner, and the job stays green; read the summary, not the colour of the check, to see whether a quarantined test works again. The Android lists (Compose, Maestro) run in a job of their own, `Quarantine (Android)`, which follows the same rules: it never fails, its step timeouts are literal and add up to less than its timeout, and its last step writes the summary and one `::warning` per runner that did not pass. The job leaves out the runners' own GitHub annotation reporters (Vitest's `github-actions`, Playwright's `github`), whose red `::error` lines would sit under the green check on files a PR may not touch; the summary and the warning carry the result. Its e2e step runs with `--retries=0` (CI otherwise retries a Playwright test once): **a quarantined test must pass without a retry to count as fixed**, and a test that fails and then passes on a retry fails here. The readers: the shared Vitest preset (`packages/testing/src/vitest.ts`, a `testNamePattern`) and `apps/web/playwright.config.ts` (`grep` and `grepInvert`) take the list of their runner through `scripts/quarantine.mjs`; with `FIVVI_QUARANTINE=only` (set by the job) they select exactly the listed tests, otherwise they leave them out. That also holds for a local run (`pnpm test`, `scripts/check.sh`), which is why a listed test is moved, not skipped: it runs in the job. Turbo takes the lists, the reader and `FIVVI_QUARANTINE` into the hash of the test tasks (`turbo.json`), so a change to a list never reuses a cached result.
  - **How an entry names a test:** its full name without file or project, as the runner prints it. Vitest: the titles of the describe blocks and of the test joined by ` > ` (`checkout > pays an invoice`); a test outside every describe is just its title. Playwright: the same titles joined by ` › ` (`checkout › pays an invoice`); the entry covers the test in every project (nl-NL and en). A name with a `|` can't be listed; a name that matches no test leaves nothing out, so check in the job's summary that the test ran there. Playwright greps the titles joined by spaces, so the names `a › b c` and `a b › c` (a describe `a` with a test `b c`, and a describe `a b` with a test `c`) are one name to it, so an entry can cover a second test whose titles run together like that.
  - **The 7 days:** the end date is at most 7 days after the added date. `scripts/quarantine.mjs` enforces it in `scripts/check.sh` and in `Checks (Linux)` (the turbo task `//#check:quarantine`, which is never cached, because a cached result would not run again when only the date passes). It fails on an entry without a bug, an added date or an end date, an end date more than 7 days after the added date, an end date that has passed, and a test with a marker below. An expired entry therefore stops every PR until its bug is fixed and the test is off the list.
  - **Never quarantined:** tenant isolation, concurrency and permission tests: fix them or revert the change that broke them. A Vitest or Playwright test of these kinds carries `@isolation`, `@concurrency` or `@permission` in its title, or in the title of a describe block around it, which is part of its full name (`test('@isolation a trainer of another workspace gets no clients', …)`), and the rule rejects a list entry whose name has one. The tenant isolation suite (`packages/api/test/isolation/`, `@isolation` on every describe block, a test keeps the file's marker), the tenant scope tests of the database package (`rls`, `tenant-scope`, `tenancy`), the role and route access tests of the API (`@permission`, and the 401, 403 and 404 cases of the feature suites), the role tests of the web e2e suite and every test that runs two requests at once (`@concurrency`) are marked; a new test of these kinds gets the marker when it is written. The form for Compose and Maestro is below (an annotation, a tag); the one for XCTest is chosen with its list reader, and tagging its existing tests is part of that work.
  - **Compose and Maestro** (E002 #1363): `quarantine/compose.txt` lists Android tests, `quarantine/maestro.txt` Maestro flows, read by `scripts/android.sh` and `scripts/maestro.sh` with `scripts/quarantine-android.mjs`. An entry names a Compose test by its class and method as JUnit prints them, `app.fivvi.pro.home.WorkspaceSwitchTest#test_F012_AC6_profileSwitchesWorkspace` (a parameterized test without its parameters, so the entry covers `nl-NL` and `en`; a class alone lists all its tests), and a Maestro flow by its file name without `.yaml`, `workspace-switch` (it covers both locales). `android.sh test`, `build` and `verify` leave the listed unit tests (a Gradle init script, `apps/android/gradle/quarantine.init.gradle.kts`) and the listed Compose UI tests (a JUnit filter the instrumentation runner loads, `QuarantineRunFilter` in `:core`) out, and `maestro.sh android` runs the other flows as files; with `FIVVI_QUARANTINE=only` (the job `Quarantine (Android)`, `WORKFLOW.md §7`) `android.sh quarantine` and `maestro.sh android` run exactly the listed ones. A name that matches no test is a warning in a required job, and in `Quarantine (Android)` a run that did not pass (reported as below; the job stays green). The marker of a test that is never quarantined can't be in its name here: a Kotlin test carries the annotation `@Isolation`, `@Concurrency` or `@Permission` (`app.fivvi.core.quarantine`, on its own line above the method, or above the class for all its tests), a Maestro flow the tag `isolation`, `concurrency` or `permission` in the `tags:` of its header, and `scripts/quarantine.mjs` rejects an entry whose test has one. The tests of the permission matrix (`WorkspaceCapabilitiesTest` and the 403 cases of the view models and screens, `test_F004_AC10_…`, `test_F006_AC10_…`, `test_F006_AC12_…` of a refused call) and of workspace isolation (the clients of the other workspace after a switch, the workspace a person is not on) carry them; a new test of these kinds gets the marker when it is written.

## 9. Agent workflow

1. Read the spec issue and your ticket. The spec's **Test plan** (§6) says which tests prove each AC; update it in the spec if the plan has to change.
2. Build with `/tdd`: write the failing test for the next vertical slice, make it pass, refactor (red-green-refactor). Bugs go through `/diagnosing-bugs`, which starts from a failing regression test.
3. Run `scripts/check.sh` (every suite, with a per-worktree `E2E_PORT`); `scripts/pr.sh create` runs `check.sh --fast` before every push, the first and the follow-ups, and `pr.sh create --full` runs `check.sh --all` when the reviewer asks or the round changed the workspace setup (`WORKFLOW.md §3`, [ADR-033](../decisions/ADR-033-go-live-mode.md)); integration and e2e run in CI.
4. **Review locally before pushing** (`/code-review`, standards and spec axes): do the tests actually assert the acceptance criteria, cover the roles and both locales, and would they fail if the feature broke? No agent review runs in GitHub. A test that can't fail is worse than no test.
5. Never mark a feature `IMPLEMENTED` in `FEATURES.md` while its Test plan has gaps.
