# Engineering Workflow

How every change gets from idea to `main`, and how we clean up afterwards. It applies equally to every AI coding agent (GitHub Copilot, Claude Code, Codex) and to humans.

## 1. Golden rules

1. **Never commit directly to `main`.** `main` is always deployable.
2. **One change = one branch = one worktree.** No exceptions, including docs and small fixes.
3. **Clean up when the change is merged.** A finished change leaves no worktree, no branch and no running process behind.
4. **Both languages, every platform the feature touches, or it isn't done.** See the Definition of Done (§6).

## 2. Branch naming

| Type | Pattern | Example |
|---|---|---|
| Ticket of a feature (`[F0xx]`) | `feature/<issue>-<slug>` | `feature/57-hold-a-spot` |
| Bug | `fix/<issue>-<slug>` | `fix/63-hold-expiry-race` |
| Ticket of an enabler (`[E0xx]`), tooling | `chore/<issue>-<slug>` or `chore/<slug>` | `chore/71-ci-cache` |
| Docs | `docs/<slug>` | `docs/roadmap` |

`scripts/flow.sh start <n>` picks the name from the issue; `scripts/wt.sh add` refuses anything else. The branch of a platform slice (below) is named after its first ticket.

- **Spec issue title:** `[F031] Open Gym public booking`; ticket titles `[F031] <slice>` (`docs/agents/issue-tracker.md`)
- **PR title:** the ticket's title, `[F031] Hold a spot during verification` (`pr.sh create` sets it)
- **Commits:** Conventional Commits with the ID as scope, e.g. `feat(F031): hold a spot during verification` (the `.githooks/commit-msg` hook checks it, and that author, committer and `Co-authored-by` are GitHub noreply addresses)

## 3. Lifecycle of a change

We follow [Matt Pocock's skills](https://github.com/mattpocock/skills). The owner only talks; the `work` skill (`.agents/skills/work/SKILL.md`) routes each step to Matt's skills and our scripts. `scripts/flow.sh status <n>` tells it where an issue is and what comes next, so a fresh session can always pick up.

| Step | Skill | Script | Result | Who decides |
|---|---|---|---|---|
| 1. Align | `grill-with-docs` | | Shared understanding; `GLOSSARY.md` and ADR proposals updated | Owner answers |
| 2. Spec | `to-spec` | `issue.sh create spec` | Spec issue `[F0xx] …`: ACs (NL/EN), Test plan, platforms, languages | Owner reviews on GitHub and approves with the `spec-approved` label |
| 3. Tickets | `to-tickets` | `issue.sh create ticket --parent --blocked-by` | Tracer-bullet sub-issues with blocking edges, `ready-for-agent` | Agents, only for an approved spec |
| 4. Build | `implement` (`tdd`) in a fresh mid-tier `builder` subagent, then `code-review` in a fresh high-tier `reviewer`, by `docs/agents/build.md` | `flow.sh start`, `check.sh` | One worktree per ticket or per platform slice, no fixed limit in parallel (ADR-021), test-first, reviewed by the `reviewer` | Agents |
| 5. Ship | `pr` | `pr.sh create`, `reviewed`, `ship` (`wait`, `smoke`, `ready`), `merge` | One draft → ready PR per ticket or platform slice, each ticket `Closes #<n>`, CI green, self-review and preview smoke check recorded for the head commit, added to the merge queue, squash-merged by GitHub | Agents queue low-risk PRs, and until pilot setup high-risk ones that are not owner-only, through the merge gate; the owner queues owner-only ones (§4) |
| 6. Clean up | | `flow.sh finish` | No worktree or branch left; the spec's next ready tickets | Agent |

Tickets that aren't agent-ready and bugs go through `triage`; bugs also through `diagnosing-bugs` (failing test first). `implement-spec` (one integration branch for a whole spec) stays available when the owner asks for it.

- Every branch has its own worktree in `.worktrees/` (git-ignored); `scripts/wt.sh add` creates it, installs dependencies and `packages/database/.env`. `scripts/check.sh` gives each worktree its own `E2E_PORT` (3200–3899), because Playwright reuses a server already running on its port. The page view tests use a second server on `E2E_PORT + 1000`, outside that range.
- If an agent tool already isolates its session in a worktree of its own (for example a Copilot or Claude Code background session), work there instead of creating a second one, with a branch named as in §2 (`git branch -m <name>`).
- **Local checks before a push** (`pr.sh create`): every push, the first and the follow-ups (review fixes, merges of `main`), runs `scripts/check.sh --fast` for what the change can affect ([ADR-024](../decisions/ADR-024-run-only-the-checks-a-change-can-affect.md), amended by [ADR-033](../decisions/ADR-033-go-live-mode.md)): the hygiene checks always; lint, types, unit tests, static checks and build for the changed packages and the packages that depend on them; shellcheck and the root script tests for scripts, hooks and other non-package files. Markdown only: the hygiene checks. A change to the workspace setup (lockfile, root `package.json`, `turbo.json`, `tsconfig.base.json`, the shared test preset) affects everything. The output says `skipped (not affected)` and why for every suite it leaves out. **What runs only in CI:** the integration tests and the web e2e tests (the output lists them as skipped, `--fast`); with `ci: fast` CI runs the integration tests on every PR and merge group, so a test that fails only there is found in a CI round, not before the push; with `ci: lean` ([ADR-035](../decisions/ADR-035-lean-pipeline.md)) both run only in the nightly run, so the builder runs the integration test files of what it touched itself (`docs/agents/build.md`, **Checks**). `pr.sh create` prints which mode ran and why; `pr.sh create --full` runs `check.sh --all`, everything, integration and e2e included, for the rare case (the reviewer asks, or the round changed the workspace setup). When the web e2e suite does run locally (`--full`, or `check.sh` by hand), it runs one at a time on the machine, so several worktrees checking at once wait for each other instead of timing out tests (#1336, [TESTING.md](TESTING.md)); run `check.sh` in the background when you expect to wait. CI is still the gate on every commit, and the merge gate (§4) requires its checks on the head commit.
- The spec's **Test plan** is written before implementing (`TESTING.md §6`).
- A ticket PR changes only its feature's `FEATURES.md` Status: the spec's first ticket sets `IN PROGRESS`, the PR that completes the spec `IMPLEMENTED` with the final one-line summary, and the others leave the file alone (`flow.sh` prints the hint). Progress lives in the spec's tickets, not in the row. The feature's ID links the spec issue.
- An API change regenerates `packages/contract` (OpenAPI + TS/Swift/Kotlin clients) in the same PR. A string change edits only `packages/i18n/*.json` and regenerates the native catalogs in the same PR.
- Every PR that touches a Railway watch pattern gets a preview (its own migrated and seeded Postgres); `pr.sh smoke` checks it and records the result in the PR description; a preview Railway skipped (after a failed first CI run, "Wait for CI") is redeployed with the `railway` CLI, in `fivvi-pr-<n>` only. Merging to `main` deploys production ([`ENVIRONMENTS.md`](ENVIRONMENTS.md)).
- Merge strategy: **squash merge** into `main`, the only method the repo allows, through the **merge queue** (§7, off with `merge: direct`): GitHub tests the PR on top of the latest `main` and merges it when the required CI checks pass, so nobody updates a branch by hand. Who adds a PR to the queue depends on its risk (§4). With `merge: direct` in `.github/pipeline.json` ([ADR-035](../decisions/ADR-035-lean-pipeline.md)) there is no queue: `pr.sh merge` squash-merges the PR itself after the whole merge gate, and the ruleset requires the branch to be up to date with `main`, so a PR that is behind `main` merges `main` in (the work skill's **Refresh**) and runs CI again first.

## 4. Working with AI agents

- **One agent per worktree.** Two agents never share a worktree or a branch.
- **Parallel work:** the factory builds at most `scripts/pipeline.sh get builders` tickets or slices at once (`.github/pipeline.json`, [ADR-035](../decisions/ADR-035-lean-pipeline.md); §8). With `builders: 1`, the setting today, **one ticket or slice is in flight at a time**: the next one starts after the previous PR merged, so it is built on a `main` that has it and the PRs never conflict; while the PR is in review, in CI or in the merge queue the factory waits for it and starts no other builder, and a PR that waits on the owner (owner-only, refused, `ready-for-human`) does not hold the next one back (`docs/agents/build.md`, **Parallel builders**). The rest of this bullet is how it works with more than 1 builder. There is no fixed limit on the tickets in progress ([ADR-021](../decisions/ADR-021-agents-queue-high-risk.md)). An optional `FIVVI_MAX_TICKETS` (a positive integer; anything else is an error) makes `flow.sh start` refuse a ticket beyond that many, and `--force` overrides it. The orchestrator starts no more agents at once than the tool's rate limits allow, and two tickets that change the same files are built one after the other, to limit merge conflicts. With `builders` above 1 the factory also keeps the 1-minute load under about 50 ([ADR-033](../decisions/ADR-033-go-live-mode.md): with no local e2e runs, the limit went from 2 to 4; 4 is what the setting said before ADR-035). The merge queue's `max_entries_to_build` (4) limits checks running at once, not tickets. **What bounds the load is slots, not the number of tickets** (#1388): a worktree that only waits for CI or the owner uses no CPU, but a booted simulator is about 250 processes, and on 13 and 14 November the load reached 500 and 700 with two simulators, parallel e2e runs and several `check.sh` and `xcodebuild` runs at once.
- **Slots for heavy jobs** (#1388): `scripts/slots.sh` gives out machine-wide slots (symbolic links in the main checkout's `.work/slots/`, shared by every worktree): 2 heavy jobs at once (`FIVVI_HEAVY_SLOTS`), and 1 job at a time with a booted iOS simulator and 1 with an Android emulator, for as long as the job runs. Three things go past that, so don't combine them with other jobs: `KEEP_DEVICE=1` leaves the simulator or emulator running after the job and its slot ended, `IOS_PARALLEL=1` boots two simulators on the one simulator slot, and `android.sh emulator` (an emulator for a dev session) takes no slot. `test-ios.sh`, `android.sh` and `maestro.sh` take their slots before they start, and `check.sh` takes one heavy slot for its whole turbo run in every mode (`--fast` too: lint, types, unit tests, build and the integration tests run in that one slot, so four builders' checks no longer load the machine at once), and its e2e suite one of its own once it has the e2e queue; a job without a free slot waits and says so every minute, naming the holders and their ages, and fails after `FIVVI_SLOT_TIMEOUT_SECONDS` (1 hour). A slot is given back when the job ends, also on failure or a kill; one whose holder is gone is taken over. `scripts/slots.sh status` lists them; `FIVVI_SLOTS=off` turns them off, and CI uses none. So run these scripts in the background when you expect to wait, and don't start a second copy of a job that waits.
- **Agent instructions live in one place.** `AGENTS.md` holds the rules for every agent; `CLAUDE.md` only imports it. Area rules live in `.github/instructions/*.instructions.md`: Copilot attaches them by path (`applyTo`), other agents read the one for the area they change.
- **Skills.** `.agents/skills/` holds our `work` skill and Matt Pocock's skills, vendored by `scripts/skills.sh` at the commit pinned in `.agents/skills.yaml` (each has a `.upstream` marker; MIT licence in `.agents/LICENSE.mattpocock-skills`). We add no agents or skills of our own that do what one of Matt's does; repo specifics go in `docs/agents/` (`build.md` for building and review). Never edit a vendored skill (the edit guard and `pnpm check` catch it): adapt behaviour in `AGENTS.md` or `docs/agents/`. To take Matt's latest version, run `scripts/skills.sh update` on a `chore/` branch and review the diff like code. Copilot and Codex read `.agents/skills/`; Claude Code reads it through the `.claude/skills` symlink.
- **Model tiers.** Shaping and every code review run on the high tier, building on the mid tier, mechanical work on the small tier; the model of each tier per tool is in `docs/agents/build.md` (**Tiers**). `.agents/agents/` defines the `builder`, `reviewer` and `mechanic` once (`tiers.json` holds the models); `scripts/agents.sh` generates `.claude/agents/`, `.github/agents/` and `.codex/agents/`, and `scripts/check.sh` fails when they differ or an agent has no tier. For Codex, see `docs/agents/codex-model-tiers.md`.
- **Scripts first.** Repetitive steps are scripts in `scripts/` (`AGENTS.md`); agents call them instead of doing the steps by hand. `scripts/bootstrap.sh` installs what they need.
- **Edit guard.** `.claude/settings.json` registers a `PreToolUse` hook, [`.claude/hooks/guard-edits.mjs`](../../.claude/hooks/guard-edits.mjs), that Claude Code and Copilot (CLI and Copilot sessions in VS Code) both run before every file edit. It denies edits in a checkout on `main` (git-ignored files such as `.env` stay editable), hand-edits of generated files (`openapi.json` and the generated clients in `packages/contract`, `packages/i18n/generated/`, the web, Swift and Kotlin outputs of `packages/design-tokens`, `packages/database/migrations/meta/`) and of vendored skills and of the generated agent definitions (`.claude/agents/`, `.github/agents/`, `.codex/agents/`). It covers the agents' edit tools, not shell commands, and only runs in folders the tool trusts. Codex and the VS Code Local agent don't run it. Its tests run in `pnpm test`.
- **Local review:** before the PR, the high-tier `reviewer` runs `code-review` on the diff on two axes, one after the other in its own context, one against `CODING_STANDARDS.md`, one against the ticket and spec (`docs/agents/build.md`). After a fix or a merge of `origin/main` it reviews only the commits since its last review (a merge by its conflict resolution) and checks that the open findings are resolved. A `builder` fixes the findings on the branch, at most two rounds, ending with a review-only round. When the `reviewer` calls both axes clean, `pr.sh reviewed` records it in the PR body for the head commit; any later push makes the record stale, so review again. **Review by risk** ([ADR-033](../decisions/ADR-033-go-live-mode.md) item 5, until pilot setup): for a PR `scripts/risk.sh` calls `low`, the review is clean with no must-fix finding left and there is at most one fix round; the should-fix findings still open go to the notes file as follow-ups, and `pr.sh reviewed --should-fix <n>` records them (add `--axes standards` for a standards-only verdict; the merge gate accepts that record only while the PR is `low`). A `high` or `owner` PR keeps the full review. The merge gate still needs a `reviewer` verdict, and the rule ends at pilot setup. **Review by setting** ([ADR-034](../decisions/ADR-034-fast-pipeline.md), `.github/pipeline.json`, `scripts/pipeline.sh get review`): with `per-pr` every PR gets both axes, as above. With `split`, a `low`-risk PR gets the standards axis only, plus a check that the builder's notes name, for every acceptance criterion of every ticket in the PR, a test that is in the diff (a missing one is a must-fix finding), and `pr.sh reviewed --axes standards` records it (the merge gate accepts that record only for a `low` PR while `split`); a `high` or `owner` PR keeps both axes. The spec axis then runs once per merged slice or ticket PR, on its squash commit, and once for the whole spec when every ticket is closed (`flow.sh` phase `spec-review`), against the map from `scripts/spec-review.sh map <spec>`; findings become bug tickets under the spec (`docs/agents/build.md`, **Spec review**).
- **Spec approval:** the owner approves a spec with the `spec-approved` label. Only then are its tickets cut and built (`flow.sh` reports `needs-approval` before). A material change to an approved spec removes the label (`issue.sh update`, unless `--minor` for a typo fix), so the owner approves again.
- **Who merges** ([ADR-016](../decisions/ADR-016-agent-merges.md), amended by [ADR-021](../decisions/ADR-021-agents-queue-high-risk.md), [ADR-023](../decisions/ADR-023-owner-out-of-the-per-pr-loop.md) and [ADR-033](../decisions/ADR-033-go-live-mode.md)): `scripts/risk.sh` classifies each PR from its changed paths (`scripts/high-risk-paths.txt`) and the `owner-merge` and `owner-only` labels on its issue or spec into three levels: `low`; `high`, with only agent-queueable reasons (the path groups the file declares with `@agent-queue`: auth, tenant data, health notes, dependencies, infrastructure, tooling, quarantine, `ci` (the CI workflows, `.github/workflows/*.yml` only, [ADR-033](../decisions/ADR-033-go-live-mode.md), until pilot setup) and billing; and the `owner-merge` label); and `owner`, with at least one owner-only reason (any other path group: the core guardrails, legal, product docs and ADRs; the `owner-only` label). Core is the rules agents work by and what decides risk, gates, phases, checks and allowlists, the agent definitions, hooks, the rulesets, `AGENTS.md`, the root `package.json` and `turbo.json`, and the files that skip tests; tooling is the test and build configs, lint rules, drift and contrast checks, `TESTING.md` and the native and release helper scripts (`scripts/high-risk-paths.txt` is the one place to read the boundary). A change to `ROADMAP.md` or `FEATURES.md` that only ticks checkboxes or moves a feature forward in its lifecycle is status-only and not owner-only (`scripts/status-only.jq`); a patch the script cannot read stays owner-only. `pr.sh create` prints the owner-only reasons of a ticket PR, so the builder can move an edit the ticket does not need to a PR of its own. Until pilot setup agents add a low-risk or a high-risk PR to the merge queue with `pr.sh merge` ([ADR-018](../decisions/ADR-018-merge-queue.md)) only when every condition holds: not owner-only, every check passed on the head commit, both `code-review` axes clean on it (for a `low` PR with no must-fix finding left, clean with its should-fix findings recorded as follow-ups: **Local review**), `pr.sh smoke` recorded for the head commit that the preview passed or that there is none, no unresolved threads, ready for review, and the merge queue has not removed that commit ("not removed from the queue"). There is no "up to date with `main`" condition: the queue tests every PR on the latest `main`. For a high-risk PR, `pr.sh merge` first records `**High-risk agent merge:**` with the commit and the reasons in the PR body, and `flow.sh next` lists the high-risk PRs agents merged in the last 7 days under "For the owner to read". `pr.sh merge` records the queued commit in the PR body, never uses `--auto` or `--admin`, and leaves the branch alone (deleting the head branch of a queued PR closes it); GitHub squash-merges the PR when the checks pass on the combined commit, and `flow.sh finish` cleans up afterwards. If the gate refuses, it queues nothing, records the refusal and its reasons in the PR body for the head commit, and the PR waits for the owner, as every owner-only PR does (the owner adds it to the queue); agents don't retry it on that commit, and a new push makes the refusal stale. If the queue removes the PR (the combined commit failed a check or timed out), `flow.sh status` shows `queue-removed` with the reason; the gate refuses that commit ("not removed from the queue"). An agent fixes a cause in the PR and pushes. For a cause outside the PR (a flaky check, a timeout, a check that also fails on `main`) it files or finds the bug and blocks the PR's issue with it: the PR is `waiting-fix`, the bug is built first, and once it is closed as completed the agent queues the same commit once more with `pr.sh merge <pr> --after <bug>` (`requeue`; [ADR-025](../decisions/ADR-025-requeue-after-a-fix.md)), once per commit. Only a removal that has no fix in code to wait for, or a second removal, is listed for the owner (`flow.sh next`). Until pilot setup an agent merge is also a production release; from pilot setup, before real personal data enters production, the owner approves production releases separately and removes the `@agent-queue` lines, so every high-risk PR goes to the owner again (`ROADMAP.md` §7, pilot setup checklist). The `billing` line goes earlier, before a live payment-provider key is set: payment code is agent-queueable only while payments run in the provider's test mode (`scripts/payment-key-guard.sh` refuses a live key while the line is there). The processor agreement (`docs/legal/verwerkersovereenkomst.md`, measure T12) says the same.
- **Run the factory:** when the owner says so, and every 2 hours on the owner's Mac (a Claude Code scheduled task, not repo code), the `work` skill builds, ships and merges every ready ticket, as many at a time as the tool's rate limits allow, until only owner items are left: specs to approve, owner-only PRs, refused PRs, PRs the merge queue removed for a cause the factory cannot fix, `needs-info` questions (`flow.sh next`). A PR in the queue waits on GitHub, not on the owner; a removed PR that waits for its bug (`waiting-fix`) waits on the bug, which is ready work. A run lock (`scripts/flow.sh lock`, a file under the main checkout's `.work/`, expiring 3 hours after it was taken or last refreshed; a live run refreshes it as it works) keeps two runs from overlapping: a run that finds a live lock reports its age and stops. This runs locally; running it unattended in GitHub Actions is a later decision.
- **No agent review in GitHub CI/CD:** do not add Copilot code review, Claude or Codex review jobs, bot PR reviewers, required agent-review status checks or required cross-agent approvals. GitHub CI is for deterministic checks such as tests, lint, generated-file drift and security scans.
- **PRs per platform slice, not per ticket** ([ADR-033](../decisions/ADR-033-go-live-mode.md), item 2): the fixed cost of a PR (CI, review, smoke check, merge group) is paid once for a slice. `scripts/flow.sh start --slice <spec> <platform>` (platform: `backend`, `web`, `ios` or `android`) takes up to 5 open, unblocked `ready-for-agent` tickets of one spec on one platform, plus a ticket blocked only by tickets of the slice, into one worktree, branch (named after its first ticket) and notes file; the builder builds them test-first, one commit per ticket. The platform is read from the ticket's title, the way tickets are named (`scripts/slice.jq`): `iOS` or `Android` in the title (`Fivvi Pro iOS: …`, `Android: …`); `Web:` or `client web` (`Client web: …`, `Foundation: Boeken on the client web …`); `API`, `DB`, `domain` or `cron` (`… (API, domain)`, `… through the API`); or one `backend`, `web`, `ios` or `android` label, which decides over the title. A ticket that names no platform, or two, is in no slice and is built alone, like a bug (`flow.sh start <n>`). `pr.sh create` adds `Closes #<n>` for every ticket of the slice and warns, but does not refuse, when the branch changes more than about 1,500 lines; keep to 5 tickets or fewer when they are big. `flow.sh status`, `next` and `finish` work from any ticket of the slice: they show the slice's branch and PR, and `finish` closes every ticket still open. A spec that touches backend + iOS + Android heavily still gets a contract ticket that blocks the platform tickets.
- **No silent contract breaks:** after a contract freeze (end of M4, end of M7), API changes are additive only.
- **Agents never** approve a PR, push to `main`, force-push shared branches, merge outside `pr.sh merge`, commit secrets, or edit generated files by hand.

## 5. Cleanup checklist (after merge)

`scripts/flow.sh finish <n>`, from the **main checkout**, checks that the PR is merged and the local branch holds nothing more, then removes the worktree, the local and remote branch and the ticket's notes, updates `main`, closes the issue if the PR didn't, and reports what the spec needs next. It ends with `scripts/clean.sh`, which also removes the worktrees of other merged PRs (and of closed PRs whose branch is pushed), folders in `.worktrees/` that are no worktree, simulators and Xcode DerivedData folders of worktrees that are gone, and turbo cache entries unused for 7 days; it never touches uncommitted or unpushed work (it lists that under "Left for you"), and `--dry-run` shows what it would remove. The Factory runs it at the start of every run, and `flow.sh next` lists a merged worktree as work (`Finish #n`, `Clean up <branch>`), so cleanup does not depend on anyone remembering.

Also make sure that:

- [ ] Dev servers, watchers, simulators/emulators and Docker containers started for this change are stopped.
- [ ] Temporary files, scratch scripts and debug output are deleted (never committed).
- [ ] Scratch Railway services or environments created for the change are deleted ([`ENVIRONMENTS.md`](ENVIRONMENTS.md)); the PR environment is deleted automatically on merge.
- [ ] When the last ticket of a spec is merged: `FEATURES.md` shows `IMPLEMENTED` with the final one-line summary, and the spec issue is closed (`flow.sh status <spec>` says `complete`, then `done`; with `review: split` it says `spec-review` first, until a clean final spec review is recorded).

## 6. Definition of Done

From `PRODUCT.md §86`, extended for native apps. A user-facing feature is **not done** unless:

- [ ] Web behaviour works where required
- [ ] iOS **and** Android behaviour works where required (parity: same screens and states on both)
- [ ] Permissions are correct (Owner / Trainer / Client)
- [ ] Tenant isolation holds (covered by the isolation suite)
- [ ] Dutch UI exists and has passed the local copy review against `packages/i18n/GLOSSARY.md`
- [ ] English UI exists
- [ ] Dates/times localize correctly (nl-NL: `22 september 2026`, `18:00`, Europe/Amsterdam)
- [ ] Relevant emails exist in nl-NL and en
- [ ] No hard-coded user-facing strings (CI enforced)
- [ ] Generated contract and string catalogs are up to date (CI enforced)
- [ ] Tests cover the acceptance criteria per the spec issue's Test plan and the checklist in [`TESTING.md §3`](TESTING.md) (e2e runs in both locales for user flows)
- [ ] Review by the `reviewer` (`code-review`, both axes; with `review: split` the standards axis per `low`-risk PR and the spec review per slice and per spec, ADR-034) completed and findings fixed (`CODING_STANDARDS.md`); a `low`-risk PR may keep should-fix findings as follow-ups until pilot setup (ADR-033)
- [ ] Spec issue up to date with what was built (ACs, languages, platforms)
- [ ] The prototype (or the website design) and `DECISIONS.md` match what was built, and the artifact is republished after the merge ([`DESIGN.md`](../../DESIGN.md#the-designs-follow-the-app))
- [ ] Feature registry status updated
- [ ] Acceptance criteria pass
- [ ] Cleanup (§5) completed after merge: `flow.sh finish` ran and `scripts/clean.sh` left no worktree, simulator or build output of the change behind

## 7. CI and required checks

CI is GitHub Actions ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)). It runs on every pull request, every push to `main`, every merge group of the merge queue (`merge_group`, `checks_requested`), on demand (`workflow_dispatch`) and every night (`schedule`, 02:00 UTC, on `main`). What a run runs depends on the **pipeline switch** `ci` in [`.github/pipeline.json`](../../.github/pipeline.json), which says `lean` today: the UI tests and the integration tests run in the nightly run, not on PRs and merge groups ([ADR-035](../decisions/ADR-035-lean-pipeline.md), [ADR-034](../decisions/ADR-034-fast-pipeline.md), "The pipeline switch" below; `fast` runs the integration tests on every PR, `full` is the setup as it was before). A new push to a PR cancels that PR's previous run; a run in progress on `main` and a run of a merge group are never cancelled (a run on `main` that is still pending when another push arrives is replaced by the newer one).

**The push run on `main` only fills the caches, and no failed step or job fails it** ([ADR-018](../decisions/ADR-018-merge-queue.md), amendment of 12 November 2026). The merge group has already passed on the tree that becomes `main`, so the run of the push tests nothing new; it stays because PRs and merge groups read only `main`'s caches and their own. It runs the Linux jobs as on a PR (with `ci: fast` without `E2E (Linux)` and without the emulator and AVD cache of `Android tests`: see the table below), so turbo caches the results of the tasks that passed in `Checks (Linux)` (`test`, `test:integration`; a task that failed is left out and the others stay; `E2E (Linux)` only restores the turbo cache and saves none, so a `test:e2e` result is not cached in CI today), and the native jobs only as far as they write the Gradle, DerivedData and AVD snapshot caches, without their test suites: `iOS build` and `Android build` (not the Maestro app and the test bundle, which only the test jobs read), `Android tests` up to the emulator boot, snapshot and stop and, in a step of its own that only a push runs, `scripts/android.sh compile-tests` (E002 #1370), which compiles the unit and instrumented test APKs of every module and assembles the release bundle without running a test, so `main`'s Gradle cache holds their dependencies and a PR's `Android tests` restores it (not `verify`), and not `iOS tests`, their retries, `Android Maestro` or the gates `iOS` and `Android`. Every job has `continue-on-error` on a push (and only on a push), as have the turbo steps, so that the job passes and the cache is saved with what passed: a flaky test or a failed download leaves its result out of the cache and the run succeeds. `continue-on-error` covers only a failure. A job that hits its job timeout ends `cancelled`, and a cancelled job makes the run `cancelled` (E2E (Linux) did on push runs 42821661674, 42761668186 and 42649049029; Railway's deployments then went inactive within seconds of the run ending, as after a failed run). So the long steps of the jobs that run on a push have a step `timeout-minutes` below their job's, on a push only (a pull request and a merge group are timed by the job alone): a hang becomes a failed step, which `continue-on-error` covers. **Still open:** no YAML can stop a cancel when no runner takes a job (the macOS jobs, after about 15 minutes with no step run); the run is then `cancelled`, and whether Railway's "Wait for CI" ([`ENVIRONMENTS.md §4`](ENVIRONMENTS.md)) still deploys is checked on the first merges (the owner check of the PR of #1357). A push run with no jobs that shows as `cancelled` was still pending when a newer push replaced it in the concurrency group; that is not a failure. The check of `main` itself is meant to be a daily full run (ADR-018, same amendment; coming, [#1358](https://github.com/fivvi-app/fivvi/issues/1358)); the nightly run of ADR-034 (below) runs every job in full every night, UI tests included. **With `ci: lean`** ([ADR-035](../decisions/ADR-035-lean-pipeline.md)) the integration tests (tenant scoping, auth, the database, API routes against real Postgres) are not a gate before the merge: the merge gate still guards `main` with lint, types, unit tests, the build and the static checks (the merge queue's run with `merge: queue`, the PR's own run on a branch that is up to date with `main` with `merge: direct`), and the integration tests run in the nightly run with the UI tests. A failure there opens `Nightly UI tests failed` (the title is kept: the factory, `flow.sh` and `usage.mjs` match it); its body names the failing suite, `Integration tests and the other Linux checks` for `Checks (Linux)` (the job's log says which task) and `UI tests and native jobs` for the others, and the factory builds it before the other tickets. **Before pilot setup** (real personal data in production) `ci` goes back to `fast` or `full` (§8). T12 of the processor agreement promises the required CI checks, which still run; this only changes which tests they hold.

**Required checks on `main`:** `Detect changes`, `Checks (Linux)`, `E2E (Linux)`, `iOS` and `Android`; `Quarantine` and `Quarantine (Android)` are not required, so a listed flaky test never blocks a PR. The ruleset in [`.github/rulesets/main.json`](../../.github/rulesets/main.json) enforces them. It also requires a PR and blocks force-pushes and deletion. With `merge: queue` it requires the merge queue and no longer requires an up-to-date branch, which the queue replaces; with `merge: direct` ([ADR-035](../decisions/ADR-035-lean-pipeline.md)) it has no merge queue and the required checks are strict: the branch must be up to date with `main`. The repo allows squash merges only ([`.github/repo-settings.json`](../../.github/repo-settings.json)). `scripts/github-settings.sh apply` applies both, and can be run again at any time. Renaming a job renames its check, so change this table and the ruleset in the same PR and apply it after the merge (a test compares the ruleset with `ci.yml`).

**Merge queue** ([ADR-018](../decisions/ADR-018-merge-queue.md)), **off with `merge: direct`** ([ADR-035](../decisions/ADR-035-lean-pipeline.md)): with one PR in flight (`builders: 1`) the queue would only run CI again on the same code, so `.github/pipeline.json` says `"merge": "direct"` today. `scripts/github-settings.sh apply` then applies the ruleset without its `merge_queue` rule and with strict required status checks (`strict_required_status_checks_policy: true`: the branch must be up to date with `main`; squash only, the same five required checks, no bypass), derived from the one file `.github/rulesets/main.json`; `pr.sh merge` squash-merges the PR with `gh pr merge --squash --match-head-commit` after the same whole merge gate, and says so when GitHub refuses because the PR is behind `main` (then the **Refresh** steps, CI, and merge again). `pr.sh merge --after` (ADR-025) refuses: there is no queue to re-queue in. The `merge_group` trigger in `ci.yml` stays for `merge: queue`. What follows describes the queue: when a PR is added to the queue, GitHub builds a temporary branch `gh-readonly-queue/main/pr-<n>-<sha>` with the PR on top of the latest `main`, and starts `ci.yml` on it with the `merge_group` event. The five required checks must report on that commit, or the queue times out and removes the PR; that is why `ci.yml` has the `merge_group` trigger. The ruleset (`merge_queue` rule) sets squash, `ALLGREEN` (every queued PR's commit must pass, not only the last), one PR per merge (a larger group would not run the checks fewer times: "Merge limits do not combine `merge_group` builds", [Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue); runs 43826697393, 43826699460 and 43826733856 for #1435, #1428 and #1429 queued within 18 seconds on 16 November, one each, stacked; on 17 November #1385, #1439 and #1310 were added one after another while the earlier ones were still queued (runs 44114527403, 44115619252 and 44117540761), one each; [ADR-033](../decisions/ADR-033-go-live-mode.md), "Merge group size"), up to four builds at once ([ADR-033](../decisions/ADR-033-go-live-mode.md); three before), and a check timeout of 160 minutes: more than `Detect changes` (5) plus the longest chain of native jobs (`iOS build` 12 then `iOS tests` 44, or `Android build` 12 then `Android Maestro` 60, and with the retries below the 154 minutes). With the 2-minute gate jobs the longest chain by timeout is 79 minutes for Android (`Detect changes` 5, `Android build` 12, `Android Maestro` 60, `Android` 2) and 63 for iOS (`Detect changes` 5, `iOS build` 12, `iOS tests` 44, `iOS` 2); a test compares the iOS numbers with the measured jobs. When no runner takes `iOS build` or a test pass, GitHub cancels the job after 15 minutes and the retry (`iOS build (retry)`, `iOS tests (<locale> <part>/3) (retry)`) tries once more (#1268), and the retry may wait for a runner for 15 minutes as well. With both stages retried the longest chain is `Detect changes` 5, then the build 15 + 15 + 12, then the tests 44 (another part's full run: the plan waits for the whole matrix) + the plan 2 + 15 + 44, then `iOS` 2 = 154 minutes; the 160 holds it, and `pr.sh wait` gives a native run 165 (a test computes that chain from `ci.yml`, keeps it under the queue timeout and under what `pr.sh` waits, and keeps the other chains under it too). `Android build` took 0.8 to 4.6 minutes in the last 46 runs, so its job has 12 and its build step 10, at least twice the slowest; the `Android Maestro` step runs both locales in 24 to 30 minutes (November 2026, #1578; 14 to 20 before), so it has 45 (1.5 times the slowest, #519) inside the job's 60, and its `Step durations` step adds a `::warning::` annotation when the flows used more than two thirds of it (`scripts/step-timings.sh`). A test keeps the Android chain (79) under the queue timeout and under what `pr.sh` waits. Measured on the last 10 green runs that ran iOS (#393): `iOS build` 2.5 to 5.4 minutes, then the `iOS tests` parts in parallel (four when this was measured; six since #1614, so each is shorter), 14 to 21 minutes, of which the simulator boot and settle is up to 4 minutes. The deadline of `scripts/test-ios.sh` is 2100 s, counted from the start of xcodebuild (1790 s until #1389); the job's 44 minutes (2640 s) hold that, the 60 s grace, the 310 s the job spends outside the deadline (boot and settle, other steps, the reports and the upload) and 2 minutes of margin. `iOS build` stays at 12 minutes: the longest build in about 400 recent runs took 400 s. `Detect changes` compares the merge group with the event's `base_sha`, so the native jobs still run only when native paths changed (see "Native jobs"). A PR is added with `scripts/pr.sh merge` (low-risk, and until pilot setup high-risk that is not owner-only; agents) or the "Merge when ready" button (the owner); never with auto-merge or the admin bypass. Railway deploys `main` only ("Wait for CI", [`ENVIRONMENTS.md`](ENVIRONMENTS.md)), so the temporary branches deploy nothing.

**Adding a check:** a new deterministic check (i18n parity, ICU syntax, OpenAPI drift, generated files up to date, …) is a `check` script in the package that owns it. `turbo run check` in `Checks (Linux)` picks it up, so the workflow file doesn't change. Keep `Checks (Linux)` under ~10 minutes (`TESTING.md §7`).

**Releases:** a build for testers is a separate, hand-started run in the protected `release` environment, which the owner approves and which only deploys from `main`; it is not part of CI. See [`RELEASE.md`](RELEASE.md).

**Native jobs:** `iOS` and `Android` run in a PR, a merge group or a push to `main` that touches the app, its generated inputs (the committed client, string catalogs, design tokens) or its own scripts, the exact paths being those in [`scripts/native-jobs.sh`](../../scripts/native-jobs.sh), and only when `apps/ios` or `apps/android` exists. The client is `packages/contract/swift/` for iOS and `packages/contract/kotlin/` for Android, not every path under `packages/contract/`: an API change that leaves both clients as they are builds nothing new, and one that should have changed them fails the contract drift check in `Checks (Linux)` ([ADR-024](../decisions/ADR-024-run-only-the-checks-a-change-can-affect.md)). A skipped job counts as passed. Markdown files (`*.md`, a README under `apps/ios`) never count as a change to those paths, so a documentation-only change to a native app runs neither job; for that no native build or test reads a Markdown file (the check that a README records the app's final bundle or application ID is a Linux test, `scripts/test/app-ids.test.mjs`, which also fails when a native source reads one). Shared files (`.github/workflows/ci.yml`, `scripts/_lib.sh`) don't run them on their own. A push to `main` or a merge group that touches none of those paths skips them (a merge group is compared with the queue's base commit, so a native change in any queued PR runs them). The `run-native` label belongs to the PR's own run; the merge group runs a native job only when a native path changed. To run them anyway, add the `run-native` label to the PR before you push (CI reads it on the PR's pushes; re-running a job doesn't pick up a label added later), or run `gh workflow run CI --ref <branch>`. Their parts run the steps of the same `scripts/test-ios.sh`, `android.sh` and `maestro.sh` as locally (`pnpm test:ios`, `pnpm test:android`, `pnpm test:maestro` run the steps one after the other), so a green check means the same as a green local run. The caches (the iOS build, the Android AVD) belong to the PR that created them or to `main`; the pushes to `main` that change native paths write the `main` caches every PR and every merge group can read (a merge group's own caches are read by nobody else), so a PR's first run is warm once `main` has run its paths. That is why a push to `main` still runs a native job when its paths changed, although the merge queue tested the same tree, but only as far as it writes a cache and without its test suites (see the push run above): without it `main` would hold no caches and every PR and queue run would start cold ([E002 #242](https://github.com/fivvi-app/fivvi/issues/242)). The cache action never overwrites an existing key: when a cached AVD snapshot stops loading, the job falls back to a cold boot but the fresh snapshot isn't saved under the same key, so bump the `v1` in the AVD cache key in `ci.yml` to rebuild it. The Android jobs stop the emulator with `scripts/android.sh stop`, which waits for it to exit before the AVD cache is saved. Every part ends with its step durations in the job summary ([`scripts/step-timings.sh`](../../scripts/step-timings.sh), and `pr.sh ship` prints those of the parts); the iOS jobs add the build timing and the slowest tests. `workflow_dispatch` and the nightly run (`schedule`) force every job, the Linux E2E job too, and so does the `run-native` label for the native jobs and the Linux E2E job (not for the UI tests: with `ci: fast` only `workflow_dispatch` and the nightly run have them).

## 8. Switching the pipeline back (ADR-034, ADR-035)

The fast pipeline of [ADR-034](../decisions/ADR-034-fast-pipeline.md) and the lean pipeline of [ADR-035](../decisions/ADR-035-lean-pipeline.md) are four settings in [`.github/pipeline.json`](../../.github/pipeline.json), and each can go back on its own. Nothing was removed: the earlier setups are the same code with other values. Tags: `pipeline-full-2026-11-18` is the full pipeline (before ADR-034), `pre-fast` is `main` as the lean pipeline was made (`ci: fast`, `review: split`, 4 builders, the merge queue).

| Setting | Lean (ADR-035) | Back to the fast pipeline (`pre-fast`) | Back to the full pipeline | What changes when it goes back |
|---|---|---|---|---|
| `ci` | `lean` | `fast` | `full` | `fast`: the integration tests (`test:integration`) run in `Checks (Linux)` on every PR and merge group again, and gate the merge. `full`: also every UI test on every PR and merge group: the iOS UI tests, the Compose UI tests on an emulator, `Android Maestro`, `E2E (Linux)` and every quarantine list, as at the tag `pipeline-full-2026-11-18`; locally, builders run the full native suites and the full `scripts/check.sh` (integration and e2e tests included) again. |
| `review` | `split` | `split` | `per-pr` | The `reviewer` runs both axes on every PR again; the spec review after a merged slice and the phase `spec-review` go away (a spec in `spec-review` becomes `complete`); `pr.sh reviewed` records both axes. |
| `merge` | `direct` | `queue` | `queue` | The merge queue (ADR-018) is back: `pr.sh merge` adds the PR to it again and GitHub tests it on the latest `main`; the ruleset has its `merge_queue` rule and the loose status policy again. **Needs `scripts/github-settings.sh apply` after the PR merges** (below): the file alone does not change GitHub. |
| `builders` | `1` | `4` | `4` | The factory runs up to that many builders at once again (while the 1-minute load stays under about 50): PRs of tickets in flight together can conflict again, and `Refresh` lines (`flow.sh next`) keep them mergeable. |

**Applying the `merge` setting (owner, after the PR that changes it has merged).** `.github/pipeline.json` only says what the scripts expect; the ruleset on GitHub is changed by `scripts/github-settings.sh apply`, which reads `merge` and applies `.github/rulesets/main.json` as is (`queue`) or without its `merge_queue` rule and with strict required status checks (`direct`). Until it has run, `pr.sh merge` prints a one-line warning and goes by what GitHub has. From the main checkout, with a token with admin rights on the repo (the owner's `gh`):

1. `git switch main && git pull` (the PR must be merged: the script reads the file in your checkout).
2. `scripts/pipeline.sh get merge` prints the value you expect (`direct` or `queue`).
3. `scripts/github-settings.sh apply`. It prints `✅ ruleset 'main' updated (merge: direct)` and then also applies the repo's merge settings, the `release` environment and the labels, as always; it can be run again at any time.
4. Check on GitHub (Settings, Rules, `main`): with `direct` no "Require merge queue", "Require branches to be up to date before merging" ticked; with `queue` the reverse.

**Owner-only PRs fall behind `main` (with `merge: direct`).** The ruleset's strict required checks make GitHub refuse the merge of a branch that is behind `main`, and every agent merge puts `main` ahead of an owner-only PR that is waiting. The factory refreshes only PRs that conflict with `main` (re-running CI on every owner PR after every merge would cost more than the button), so: when the merge box says the branch is out of date, press **Update branch** (it merges `main` into the PR; CI runs once more), wait for the checks, then merge. `scripts/flow.sh next` says so on the PR's line (`behind main: press Update branch …`). When the update conflicts, the PR is `CONFLICTING` and goes through the Refresh steps of the `work` skill. With `merge: queue` none of this applies: the queue tests the PR on the latest `main`.

**Pilot setup requires leaving `ci: lean`.** Before real personal data enters production (the owner's pilot setup, `docs/legal/`), `ci` goes back to `fast` or `full`, so that the integration tests (tenant scoping, authorization, the database) gate every merge again; `merge` may stay `direct`, or go back to `queue` if the owner wants the queue's re-test of every PR on the latest `main`. T12 of the processor agreement promises the required CI checks of the merge queue; they still run with `lean`, but the integration tests are not among them, and that is not acceptable once clients' data is in the system. `builders` may stay at 1.

**The owner asks an agent**, for example "switch the pipeline back to full", "turn the UI tests back on for every PR" or "go back to both reviews on every PR". The agent:

1. Makes a worktree: `scripts/wt.sh add chore/pipeline-<setting>-<value>` (for example `chore/pipeline-ci-fast`).
2. Sets the value in `.github/pipeline.json`: `"ci": "fast"` (or `"full"`), `"review": "per-pr"`, `"builders": 4`, `"merge": "queue"`, or several. **To go back to `pre-fast`**: `{"ci": "fast", "review": "split", "builders": 4, "merge": "queue"}`, and, after the PR has merged, `scripts/github-settings.sh apply` (above) to bring the merge queue back on GitHub. Nothing else in the code changes; `scripts/pipeline.sh get ci|review|builders|merge` must print the new value.
3. Adds one line to the **Status** of ADR-035 (for `ci`: `lean` to `fast` and `builders`) or of ADR-034 (`full`, `review`): the date, the setting, the new value and the owner's reason. Going back is decision 5 of ADR-034 and the consequences of ADR-035, so it needs no new ADR; going back *and* removing the fast pipeline's code would.
4. **When `review` goes back to `per-pr`:** measure T12 of the processor agreement (`docs/legal/verwerkersovereenkomst.md`, the Dutch and the English row, same meaning) goes back to its version 0.6 wording. Replace the whole span version 0.7 added, from "before the pull request an agent reviews the change locally against the coding standards" up to and including "before the specification is closed;" (Dutch: the same clauses), with "before the pull request, two agents review the change locally (coding standards and specification);", and "the agent reviews before the pull request" with "the two agent reviews". Take the exact 0.6 text from git: `git log -p -- docs/legal/verwerkersovereenkomst.md` (the commit that made it 0.7 shows both). Bump the version and add a change entry naming ADR-034 decision 5. A change of `ci` alone leaves T12 as it is.
5. Runs `scripts/check.sh`, the `reviewer`, and `scripts/pr.sh create`, `reviewed` and `ship` as for any change (the `work` skill, **Ship**). The PR is owner-only (`.github` is core guardrails, `docs/legal` legal and `docs/decisions` product docs, all owner-only groups in `scripts/high-risk-paths.txt`), so the owner merges it: adds it to the merge queue (`merge: queue`) or merges it with GitHub's button (`merge: direct`; see "Owner-only PRs fall behind `main`" above).
6. **Work in flight, when `review` goes back to `per-pr`** (before the owner queues the switch, or right after it merges, before any other `pr.sh merge`). The merge gate is no safeguard here: `pr.sh merge` reads the setting from `.github/pipeline.json` in the PR's own checkout, so a branch made before the switch still says `split` and its gate still accepts a standards-only record, until `main` (with the switch) is merged into that branch.
   - **Open PRs with a standards-only review:** find them with `gh pr list --state open --search '"standards only" in:body'` and read each one's `**Self-review:**` line; every PR whose line says `(standards only)` gets a fresh `reviewer` on both axes for its head commit and a new record with `pr.sh reviewed`, before anyone runs `pr.sh merge` on it.
   - **Specs:** list the open specs once, before the switch merges if you can: `gh issue list --state open --label spec --limit 200 --json number,title` (without `--limit`, `gh` returns only 30). `scripts/spec-review.sh status <spec>` doesn't read the switch, so it works before and after the merge (`scripts/flow.sh next` lists `Review spec #n` only while the main checkout still says `split`).
     - A spec whose tickets are all closed and whose `status` says not covered gets its final spec review.
     - A spec still building gets a slice review for each of its slice or ticket PRs merged before the switch (later ones had both axes on the PR; the PRs that closed its sub-issues, `scripts/spec-review.sh map <spec>`) that has no record line `| slice PR #<pr> |` in `.work/spec-<n>/spec-review.md` of the main checkout (the lines `spec-review.sh record` writes: `- <time> | slice PR #<pr> | clean or not-clean | findings <n> | origin/main <sha>`; a final review's line says `| final |`). `status` reads only final reviews, so it can't find these.
     - Both as `docs/agents/build.md`, **Spec review**, says. What the agent can't finish goes to the owner as a list, so the owner decides whether those specs go on without it.
   A change of `ci` or `builders` alone needs neither.
7. After the merge, nothing else needs doing: CI, the gates, the merge gate, `flow.sh`, the `work` skill and the factory read the setting from the checkout they run in, so they follow it on `main` and in every branch made or updated from `main` after the merge (the factory starts each run by updating the main checkout). The nightly run stays as an extra check; with `full` it finds what the PRs already found. The factory's scheduled prompt follows the skill on `main`, so it needs no edit (the prompt before ADR-034 is kept on the owner's Mac in `.work/factory-prompt-before-adr034.md`).
8. To see what going back changed, compare snapshots as `docs/agents/build.md` (**Usage**) describes: `docs/agents/usage/2026-11-18-full-pipeline.json` is the full pipeline before ADR-034.

**Going lean or fast again** is the same steps with the values of the table's first column (`lean`, `split`, `1`, `direct`; T12 as in version 0.7), and `scripts/github-settings.sh apply` after the merge for `merge` ("Applying the `merge` setting" above).
