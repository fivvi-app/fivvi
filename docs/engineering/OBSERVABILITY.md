# Observability

What Fivvi reports about itself, and what it never sends ([ADR-013](../decisions/ADR-013-observability.md), spec [#32](https://github.com/fivvi-app/fivvi/issues/32)). Errors go to **Sentry (EU region)**, product events and page views to **PostHog (EU Cloud)**. This document covers error reporting for the API, the cron job and the web app (server and browser), server product events (§4) and the web app's page views (§5). Per native app:

- Android: crash reporting, §1 "Android".
- iOS: crash reporting, §1 "iOS".

## 1. Error reporting

`packages/observability` owns every Sentry call in TypeScript. Apps and other packages call its functions (`createErrorReporter()`, `createRequestErrorHandler()`, `initBrowserErrorReporting()`, `publishSourceMaps()`) and never import `@sentry/*` themselves: Biome's `noRestrictedImports` rule (root `biome.json`) fails lint when they do.

| Runtime | What is captured | Sentry project |
|---|---|---|
| API (`packages/api`, inside the Next.js server) | Every unhandled error in a route. The caller gets the generic `500 Internal Server Error` text, with no stack trace or internal message. `HTTPException`s that a route throws on purpose are not reported | `web` |
| Web server (`apps/web/instrumentation.ts`) | Every error thrown while rendering a page: server components, server actions, and route handlers outside the API (Next.js's `onRequestError`). The visitor gets the error page | `web` |
| Web browser (`apps/web/instrumentation-client.ts`) | Every uncaught error and unhandled promise rejection in the browser, including a component that throws while rendering. A future error boundary (`error.tsx`) that catches an error itself reports it with `captureError` | `web` |
| Cron (`apps/cron`) | A failed run. The error is sent and flushed (at most 2 s) before the process exits with code 1 | `cron` |
| Android (`apps/android`) | Every crash (uncaught exception) and ANR (app not responding), and errors the app catches and reports with `Observability.captureError()`; sessions for the crash-free rate. Details in "Android" below | `android` |
| iOS (`apps/ios`) | Every crash, app hang and watchdog termination, and errors the app reports with `ErrorReporting.capture(_:)`; sessions for the crash-free rate. Details in "iOS" below | `ios` |

Not captured: health check failures (they answer `503` and log to the console), validation errors (`400`), `notFound()` and redirects, and other expected responses.

Every event carries:

- `environment`: `production`, `preview` (PR environments) or `development` (Railway's `development` environment, and local), from `RAILWAY_ENVIRONMENT_NAME`;
- `release`: the commit SHA of the deploy, from `RAILWAY_GIT_COMMIT_SHA`;
- for API errors, the route template as served under `/api` (`transaction` `POST /api/v1/clients/:clientId`, tag `route`), never the real path; for web server errors, the page's route template (`GET /clients/[clientId]`).

The browser gets `environment` and `release` from the same two variables, inlined into the bundle at build time with `NEXT_PUBLIC_SENTRY_DSN` (`next.config.ts`; Railway passes them to the Docker build).

How it is set up:

- **Off without a DSN.** Without `SENTRY_DSN` (local development, unit, integration and e2e tests, CI), `createErrorReporter()` returns a reporter that does nothing: no SDK client, no network call, nothing fails. Without `NEXT_PUBLIC_SENTRY_DSN`, the browser installs no handler and sends nothing. The variables per environment are in [ENVIRONMENTS.md §7](ENVIRONMENTS.md#7-variables).
- **Errors only.** Tracing, profiling, session replay, sessions and client reports are off, in the browser too. Each server runtime gets its own Sentry client: no auto-instrumentation and no global error handlers. The browser client has only the global handlers for uncaught errors, linked errors (`cause`), deduplication and the page URL.
- **No data collection by the SDK.** Sentry v11 collects user info, cookies, headers, bodies and query strings by default (`dataCollection`; the old `sendDefaultPii` option is gone). Every client switches all of it off (`NO_DATA_COLLECTION`), so Sentry never infers the visitor's IP address (`infer_ip: never`).
- **Scrubbed in the process.** Every event and breadcrumb passes the scrubber (§2) in `beforeSend` and `beforeBreadcrumb`, before it leaves the process.
- **Defence in depth (owner setup, #47).** The Sentry projects also have the server-side data scrubber and "Prevent storing of IP addresses" switched on.

### Source maps

Production stack traces from the web app map to the original TypeScript, and nobody can download the source maps from the web app:

1. `next build` writes source maps for the browser (`productionBrowserSourceMaps`) and the server, with a debug ID in every bundle and its map (`turbopack.debugIds`, `next.config.ts`). The SDK sends the debug IDs with each event, which is how Sentry finds the matching map.
2. `apps/web/scripts/publish-source-maps.ts` (`publishSourceMaps()`) then uploads the maps in `.next/static` and `.next/server` to the Sentry project `web` with `sentry-cli`, tagged with the release. It needs `SENTRY_AUTH_TOKEN`, an organisation auth token (it carries the organisation and the EU region), which only exists during the Docker build.
3. It then deletes every `*.map` from `.next`, including the standalone server, before the client assets are copied into it. `/_next/static/**/*.map` answers `404`; the bundles keep their `sourceMappingURL` comment, which points at nothing.

`sentry-cli` verifies Sentry's certificate with OpenSSL and the system CA store, which the slim Node image lacks, so the Docker build stages install `ca-certificates` (#87). The runtime image doesn't: nothing there shells out, and Node's TLS (the server's Sentry and PostHog clients) uses its bundled CA store.

Without `SENTRY_AUTH_TOKEN` (local, CI, previews without a token), nothing is uploaded and nothing talks to the network; the maps are still deleted. A failed upload warns in the build log but doesn't fail the build: a Sentry outage must not block a deploy, at the cost of unmapped stack traces for that release.

### Android

The app reports to the Sentry project `android` with the Sentry Android SDK (`io.sentry:sentry-android-core`).

- **One module.** `app.fivvi.pro.observability` (`apps/android/app/src/main/kotlin/app/fivvi/pro/observability/`) owns every Sentry call: `Observability.start()`, called by `FivviApplication`, and `Observability.captureError()`. ktlint's `fivvi:no-sentry-outside-observability` rule fails on an `io.sentry` import or call anywhere else, as Biome does for TypeScript.
- **The SDK library only.** No Sentry Gradle plugin (it uploads mappings and calls Sentry during the build), no session replay or NDK module, and no product analytics SDK: product events from the app are captured by the API (§4). `checkNoAnalyticsSdk` (`apps/android/app/build.gradle.kts`) fails every build whose release would ship PostHog, Firebase Analytics, Amplitude, Mixpanel or Segment, or Sentry's replay or NDK module.
- **Off without a DSN.** The DSN comes from the build configuration ([ENVIRONMENTS.md §7](ENVIRONMENTS.md#7-variables)): `fivvi.sentryDsn` for debug builds, empty unless a developer sets it for a test, and `fivvi.releaseSentryDsn` for release builds. Without one, `Observability.start()` doesn't start the SDK, and the manifest removes the SDK's own start-up providers (`SentryInitProvider`, `SentryPerformanceProvider`) and turns its auto-init off, so no Sentry code runs and nothing is sent.
- **Environment and release** from the build: `environment` is `development` for debug builds and `production` for release builds (there are no preview builds of the app); `release` is `app.fivvi.pro@<versionName>+<versionCode>`, Sentry's convention for Android, e.g. `app.fivvi.pro@0.1.0+1`.
- **Errors and crash-free sessions.** Session tracking is on: a session starts when the app comes to the foreground after more than 30 s in the background, and Sentry reports the crash-free rate per release. Tracing, profiling, session replay, screenshots, the view hierarchy and client reports are off. ANR detection stays on.
- **No data collection by the SDK.** As on the server, every `dataCollection` option is off (no user info, so no IP address, and no cookies, headers, bodies, query strings, file paths or database queries); `sendDefaultPii` is deprecated in SDK 8 and off.
- **Scrubbed in the app.** `beforeSend` and `beforeBreadcrumb` apply the §2 rules (`Scrubber.kt`). A crash is scrubbed before the SDK stores it on the device; it is sent at once, or at the next start if the app dies first. Where Android differs from §2: no tag is kept (the app has no route tags); the workspace UUID sits in the user's `data` as `organization_id`, the Java SDK's place for extra user fields; the `device` context loses its `name`, which a person may have set to their own; the format parameters of a message, `server_name` and a stack frame's held lock (`lock`, which describes the locked object) are dropped.
- **The installation ID and the account.** The SDK creates a random UUID per installation, stored in the app's files, and writes it as 32 hex characters without dashes (`0123456789abcdef0123456789abcdef`). It is the session's distinct ID and, while nobody is signed in, the event's `user.id`; Sentry counts crash-free users with it. It identifies an installation, not a person, and isn't linked to any of our records. The scrubber keeps a `user.id` that is a dashed UUID or this dashless form, exactly as the SDK wrote it so it still matches the session; anything else (an email address, a name, a hex string of another length) is dropped with the whole user. Once `GET /api/v1/me` has answered, and only if the person is still signed in with the sign-in the screen was opened for, the app sets the account `id` (the internal user UUID) as the user with `Observability.setUser()`, so later events carry it instead; on sign-out, whether the person signed out or the API rejected the token, `Session` calls `Observability.clearUser()` and the installation ID is back. No email address, name or IP address goes with it, and the workspace UUID stays unset until workspaces exist (F002). With reporting off, both calls do nothing.
- **Stack traces.** Release builds aren't minified yet, so stack traces are readable. When distribution (E017) turns on R8, it uploads the mapping files; native (NDK) crashes aren't captured.

### iOS

The app reports to the Sentry project `ios` with `sentry-cocoa` (Swift Package Manager): crashes (signals, Mach exceptions, uncaught Objective-C and C++ exceptions), app hangs and watchdog terminations (the system ending the app, e.g. for memory), with the stack traces of every thread, and errors the app reports itself with `ErrorReporting.capture(_:)` (an error it handled but that shouldn't happen; none yet). A crash is written to disk when it happens and sent the next time the app starts. Every app start begins a session, which ends as crashed or healthy: that gives the crash-free session rate.

- **One module.** `apps/ios/FivviPro/Observability/` is the only code that talks to `sentry-cocoa`: `ErrorReporting.start()` at launch, `ErrorReporting.capture(_:)`, and the scrubber. SwiftLint's `no_direct_sentry` rule (`apps/ios/.swiftlint.yml`, fixture `lint/fixtures/DirectSentry.swift`) fails anywhere else that imports Sentry or calls `SentrySDK`, as Biome does for TypeScript.
- **No analytics SDK.** Product events from the app are captured by the API (§4). `pnpm test:ios` fails on any Swift package in `Package.resolved` that isn't on its allowlist (`swift_packages` in `scripts/test-ios.sh`).
- **From the build configuration.** `FIVVI_SENTRY_DSN` and `FIVVI_SENTRY_ENVIRONMENT` in `apps/ios/Config/*.xcconfig`, read from Info.plist ([ENVIRONMENTS.md §7](ENVIRONMENTS.md#7-variables)). Release reports as `production` and Debug as `development`. `release` is `app.fivvi.pro@<version>+<build>` (`MARKETING_VERSION`, `CURRENT_PROJECT_VERSION`), Sentry's format for app releases. Until distribution (E017) raises the build number for every upload, all builds report the same release, so the release doesn't yet tell builds apart the way the server's commit SHA does.
- **Off without a DSN.** Debug's committed DSN is empty, so local builds, the unit and UI tests and CI start no SDK and make no network call; `pnpm test:ios` fails if it isn't empty. A developer can set one in the git-ignored `Config/Local.xcconfig` for the manual check in §3; while it is set, every Debug run of the app reports, tests included.
- **Errors and release health only.** Tracing, profiling, session replay, screenshots, view hierarchies, Sentry logs, client reports and captured HTTP failures are off (API errors are reported by the server). `sendDefaultPii` is off, so the SDK adds no IP address and asks Sentry not to infer one (`infer_ip: never`).
- **Scrubbed in the app.** `beforeSend` and `beforeBreadcrumb` run `Scrubber` (`Observability/Scrubber.swift`), the rules of §2 in Swift. Three differences for a phone: an event keeps its threads (a crash's stack trace is in them), with frame variables dropped; `server_name` is dropped, because on a phone it would be the device name; and an exception's `mechanism` loses its description as well as its `data`, because for an `NSError` both hold its whole `userInfo`. A reported error keeps its description as the exception value, with only email addresses masked: `NSDebugDescriptionErrorKey`, or for a Swift error the whole printed error (`String(describing:)`), associated values included. So an error, its cases and their associated values carry IDs only, never names, email addresses or note content (§2). Breadcrumbs are scrubbed when they are recorded, so a crash report stored on the device never holds an unscrubbed one. The event is edited in place, because it carries state the SDK still needs (e.g. whether it is a crash); `test_E009_AC8_scrubberDecidesEveryField` lists what happens to every field of the SDK's event types and fails when a new `sentry-cocoa` version adds one, so a new field never leaves the app unreviewed.
- **Pseudonymous IDs.** Without a signed-in user, Sentry gives an event the install's random ID (a UUID it generates on first launch and that is gone when the app is deleted) as `user.id`, and sends it with each session to count crash-free users. The `app` context carries a hash of device and app (`device_app_hash`). Neither is linked to a person in Sentry. Once `GET /api/v1/me` has answered, and only if the screen is still there and a token is still stored, the app sets the account `id` (the internal user UUID) as the user with `ErrorReporting.setUser(_:)`, so later events carry it instead of the install's ID; on sign-out, whether the person signed out or the API rejected the token, `Session` calls `ErrorReporting.clearUser()` and the install's ID is back. No email address, name or IP address goes with it, and the workspace UUID stays unset until workspaces exist (F002). With reporting off, both calls do nothing.
- **Defence in depth (owner setup, #47).** The Sentry `ios` project also has the server-side data scrubber and "Prevent storing of IP addresses" switched on. dSYMs for symbolicated stack traces are uploaded as part of distribution (E017).

## 2. Scrubbing rules

The scrubber (`scrubEvent`, `scrubBreadcrumb`) is a pure allowlist: whatever isn't listed as kept is dropped, so a new SDK field never leaks by default.

| Part of an event | Kept | Dropped |
|---|---|---|
| Error message (`exception.value`, `message`) | The text, with email addresses masked as `[email]` and the value of a `token`, `code` or `returnTo` query parameter (a sign-in link token or code, or the page asked for before sign-in, in a quoted URL) masked as `[redacted]` | Email addresses, link tokens and codes in a URL; the page asked for (`returnTo`) |
| Stack frames | File, function, line, column, source lines | Local variables (`vars`) |
| Request | HTTP method; URL without query string and fragment, emails masked; headers `accept`, `accept-language`, `content-length`, `content-type` | Body (a sign-in request's email address and code), cookies, query string (a sign-in link's token), `Authorization` and every other header (also `x-forwarded-for`), environment (`REMOTE_ADDR`) |
| User | `id` (internal user UUID; in the apps, the installation ID while nobody is signed in) and `organization_id` (workspace UUID), only when they are UUIDs (Android also accepts a UUID written without dashes, the SDK's installation ID) | Email, name, username, IP address, location |
| Tags | `route` (a route template) | Everything else |
| Contexts | `app`, `cloud_resource`, `culture`, `device`, `os`, `runtime`, `trace`; `response.status_code` | Everything else, including custom contexts |
| `extra`, `modules`, `threads` | Nothing | All |
| Breadcrumbs | Type, category, level, timestamp; `data.method`, `data.status_code`, `data.url` (without query string) | The message (a log line that may hold any text) and all other data |

The Android app applies the same rules in Kotlin, with the differences listed in §1 "Android".
The iOS app applies the same rules in Swift, with the differences listed in §1 "iOS".

UUIDs, route templates, HTTP methods and status codes stay, so an error can still be traced to a record and a route.

**The scrubber can't recognise a name or note text inside an error message.** That is why the message is the one free text we keep, and why our errors never contain names, email addresses or note text: put IDs in messages, never user content ([ADR-013](../decisions/ADR-013-observability.md): no personal data or note content in events, error messages or breadcrumbs). `EmailSendError` in `packages/email` is an example.

## 4. Product events

Server code sends product events to **PostHog EU** (EU Cloud, Frankfurt), at the host in `POSTHOG_HOST`, with one typed function, `track()`. It only accepts events from the catalog (§4.3), with only the properties the catalog lists for them. Product events from the native apps are captured here too, when the API handles the action: the apps have no analytics SDK.

### 4.1 How it is set up

- **One entry point.** `packages/observability` owns every PostHog call on the server. `apps/web/server/product-events.ts` is the one place that creates the sender, `createProductEvents({ errorReporter })`, and it has two users: the API, which gets it as the `productEvents` dependency (a route calls `dependencies.productEvents.track(event)` after the action succeeded), and sign-in, which gets it as `createAuth({ productEvents })` (`packages/auth`). Apps and other packages never import `posthog-node`: the same Biome `noRestrictedImports` rule as for Sentry fails lint when they do.
- **Production only, off without a key.** Without `POSTHOG_KEY` (development, previews, local, tests, CI), `track()` still checks the event but sends nothing and makes no network call ([ENVIRONMENTS.md §7](ENVIRONMENTS.md#7-variables)).
- **The host comes from `POSTHOG_HOST`** ([ENVIRONMENTS.md §7](ENVIRONMENTS.md#7-variables)). There is no host in code and no default to fall back on. A key without `POSTHOG_HOST`, or a host that isn't an `https://` URL, is a configuration error: `createProductEvents()` logs it and reports it to Sentry (`PostHogConfigError`) once, when it reads the config, and then sends nothing, like without a key.
- **Flushed per request, never failing it.** Each event is sent straight away, and the API waits for it after every request (`flush()`, at most 1 s). A failed or slow PostHog never fails or blocks the request: `flush()` never throws.
- **What leaves the process:** the event name, `distinct_id`, the catalog properties, a timestamp and an event UUID, plus the SDK's own `$lib`, `$lib_version`, `$is_server` and `$geoip_disable: true`. GeoIP lookup and exception autocapture are off, and there is no feature flag key, so the SDK makes no other calls. The request to PostHog comes from our server, so PostHog never sees a visitor's IP address.

### 4.2 Rules for an event

- **Name:** `snake_case`, past tense, object first: `booking_confirmed`, `workout_logged`. Property names are `snake_case` too. Use the terms of `GLOSSARY.md`.
- **Properties** are made with `property` (`packages/observability/src/event-schema.ts`) and can only be: `uuid()`, `enum([...])`, `boolean()`, `number()`, `date()` (ISO date), `dateTime()` (ISO date and time) and `optional(...)` of one of those. **Never free text:** no names, email addresses, note or workout content, or URL parameters ([role-mapping.md](../legal/role-mapping.md) D4). `defineCatalog()` throws when the module loads if a property is anything else, e.g. `z.string()`, or a name isn't `snake_case`.
- **`distinct_id`** is the internal user UUID. For an anonymous visitor (a booking page visitor before verification), use `anonymousDistinctId()`: a random UUID for that request, never stored. Link the steps of an anonymous funnel through record UUIDs in the properties (e.g. the hold's ID), not through the visitor.
- **Checked twice.** The type of `track()` rejects an unknown event, an extra property and a value outside an enum at compile time. At runtime, every event is checked against its strict zod schema. Outside production, a rejected event throws a `ProductEventError`, so a test or a developer sees it at once. In production it is dropped and reported to Sentry as a warning that names the event and the failing property, never a value; the request carries on.
- **Versioning:** an event's name and the meaning and type of its properties never change once it is live, so old and new data stay comparable. Adding an optional property is fine. Anything else is a new event with a new name (e.g. `booking_confirmed_v2`); mark the old one `Retired` in §4.3 and stop sending it.

How to add an event:

1. The feature spec names the event, its properties and the metric it serves (e.g. `ROADMAP.md §8`).
2. Add it to `PRODUCT_EVENT_CATALOG` in `packages/observability/src/catalog.ts`.
3. Add or update its row in §4.3, with status `Live`.
4. Call `track()` where the action succeeds, with the route's `productEvents` dependency.
5. Test it through the capture transport: pass `createProductEvents({ env: { POSTHOG_KEY: 'phc_test', POSTHOG_HOST: 'https://posthog.example.test' }, transport: createProductEventCaptureTransport(), errorReporter })` to the API and assert on `transport.events`, i.e. what PostHog would receive.

### 4.3 Event catalog

The live events are the two of sign-in (F001, spec [#128](https://github.com/fivvi-app/fivvi/issues/128)), `workspace_created` (F002, spec [#170](https://github.com/fivvi-app/fivvi/issues/170)), `language_changed` (F010, spec [#175](https://github.com/fivvi-app/fivvi/issues/175)), `team_member_removed` (F003, spec [#171](https://github.com/fivvi-app/fivvi/issues/171)) and `client_added` (F006, spec [#174](https://github.com/fivvi-app/fivvi/issues/174)). `packages/auth` records the sign-in events. On the web the sign-in endpoints are Better Auth's, mounted at `/api/auth`, not API routes, and its handler flushes the events before it returns. The native routes `/v1/sign-in/request` and `/v1/sign-in/token` are API routes that run the same endpoints through `auth.api`, so they record the same events, and the API flushes the shared sender after every request (§4.1). Neither carries the email address, a code, a link token, the IP address or the user agent, and `sign_in_requested` carries no account ID (AC16):

| Event | Status | Feature | `distinct_id` | Properties | Measures |
|---|---|---|---|---|---|
| `sign_in_requested` | Live | F001 Authentication | A random ID for the request (`anonymousDistinctId()`), never stored: there is no account ID before sign-in | None | Sign-in requests, to compare with `signed_in` and see sign-in problems (emails that never lead to a sign-in). Recorded for every address alike, whether or not it has an account, so the event never tells who has one; a request the rate limits (AC10) refuse is not recorded |
| `signed_in` | Live | F001 Authentication | The internal user UUID | `method`: `code` or `link`; `new_account`: `true` when this first sign-in of an allowed address created the account | Sign-ins by code and by link; new accounts. Recorded when the code is entered or the link is confirmed (not when the link is opened), after the session is created |

## 5. Page views

The web app sends a page view to **PostHog EU** (EU Cloud, Frankfurt), at the host in `POSTHOG_HOST`, for every page a visitor opens, in cookieless mode: no cookie, no browser storage, no consent banner ([ADR-013](../decisions/ADR-013-observability.md)). This covers every web page, including the public booking pages (M5) and the client pages, from day one.

### 5.1 How it is set up

- **One entry point.** `packages/observability/page-views` owns every `posthog-js` call. The root layout (`apps/web/app/layout.tsx`) reads the key and host with `readPageViewsConfig(process.env)` and renders `<PageViews>` (`apps/web/app/page-views.tsx`), which calls `capturePageView({ key, host })` on load and after every client-side navigation to a new path. Apps never import `posthog-js`: the same Biome `noRestrictedImports` rule as for Sentry and `posthog-node` (§4.1) fails lint when they do.
- **Production only, off without a key.** Without `NEXT_PUBLIC_POSTHOG_KEY` (development, previews, local, tests, CI) the layout renders nothing: the browser never loads `posthog-js` and makes no request to PostHog ([ENVIRONMENTS.md §7](ENVIRONMENTS.md#7-variables)).
- **The key and host are read at request time**, despite the key's `NEXT_PUBLIC_` prefix: the server passes them to the browser, so the SDK is a separate chunk that is only fetched when there is a key. Setting or clearing it needs no rebuild, and one build serves both cases in the e2e tests.
- **The host comes from `POSTHOG_HOST`**, with the same rules as for product events (§4.1). When the host makes page views a configuration error, the layout renders nothing, and the web server logs the error and reports it to Sentry once, when it starts (`register()` in `apps/web/instrumentation.ts`): the layout reads the config on every request.
- **No SDK features.** The package loads `posthog-js`'s slim build without remote scripts (`posthog-js/dist/module.slim.no-external`): autocapture, heatmaps, session recording, surveys, web experiments and the other extensions are not in it. Every option that collects or stores anything is off as well (`OPTIONS` in `src/page-views.ts`), so nothing depends on SDK defaults: no page leave, no web vitals, no exception capture, no remote config or feature flags (`advanced_disable_flags`), no referrer or campaign parameters, no person profiles (`person_profiles: 'never'`).
- **Cookieless.** `cookieless_mode: 'always'` with `persistence: 'memory'`: every event carries `distinct_id` `$posthog_cookieless`, and PostHog counts unique visitors with a daily hash it makes on its servers. The SDK writes no cookie and keeps nothing in `localStorage` or `sessionStorage`. The one storage call it makes is a check, at start-up, whether `localStorage` works: it writes the fixed value `xyz` under `__mplssupport__` and removes it at once, so nothing stays behind. Cookieless events are only ingested when cookieless mode is switched on in the PostHog project settings (owner setup, #47).
- **Path only.** The SDK's `before_send` runs `scrubPageView()`, an allowlist like the Sentry scrubber (§2): only `$pageview` events leave; `$current_url` is cut down to origin and path (no query string, no fragment); and only the properties PostHog needs are kept: the project key, `distinct_id`, `$cookieless_mode`, `$process_person_profile`, the SDK's `$lib`, `$lib_version`, `$insert_id` and `$time`, `$current_url`, `$host` and `$pathname`, and `$browser`, `$browser_version`, `$os`, `$os_version`, `$device_type`, `$raw_user_agent` and `$timezone`. Everything else is dropped, including the page title, the referrer, the browser language, screen sizes and person properties (`$set`, `$set_once`). The PostHog entries in [sub-processors.md](../legal/sub-processors.md) and [role-mapping.md](../legal/role-mapping.md) (D4, P4, F7) describe this list. Only the owner changes legal docs, so a change to this list waits until the owner has updated the legal docs to match.
- **Paths hold IDs, never names.** A path like `/clients/<uuid>` is sent as it is, so routes put record UUIDs in the path and never names, email addresses or other personal data.
- **Bots are dropped.** `posthog-js` drops events from browsers that look automated (`navigator.webdriver`, a `HeadlessChrome` brand), which keeps crawlers out of the pilot metrics.
- **Never breaking a page.** `capturePageView()` never throws: when an ad blocker blocks the SDK or PostHog, the page view is lost and nothing else happens.
