# Building a ticket

How a ticket is built and reviewed in this repo. A mid-tier **builder** runs `implement` (with `tdd`) and commits. A high-tier **reviewer** then runs `code-review` on the head commit, on the axes `scripts/pipeline.sh get review` and the PR's risk ask for (**Review by risk**), and, once a slice or ticket PR of a spec has merged, checks what it merged against the spec (**Spec review**). The `work` skill runs both as subagents and gives each its brief: the issue number, worktree, notes path and the `Hint` from `flow.sh`, and for a fix the findings, failing checks or PR threads to address.

## Tiers

The agents are defined once in `.agents/agents/` (`builder.md`, `reviewer.md`, `mechanic.md`, `tiers.json`) and generated for each tool by `scripts/agents.sh`; the model of each tier per tool is pinned there. Claude Code takes an alias (`opus`, `sonnet`) or a full model id; the small tier uses `claude-haiku-5-5`, because the `haiku` alias still resolves to Haiku 4.5. Copilot takes a list of model names and uses the first one available: the Copilot CLI id (`claude-sonnet-5.5`) and the VS Code qualified name (`Claude Sonnet 5.5 (copilot)`). Codex takes a model and a reasoning effort per role; see [codex-model-tiers.md](codex-model-tiers.md). Checked on 2026-10-17: `copilot --agent <name>` ran on `claude-sonnet-5.5`, `claude-opus-5.5` and `claude-haiku-5.5`, and `claude --agent <name>` reported `claude-sonnet-5-5`, `claude-opus-5-5` and, for the `haiku` alias, `claude-haiku-4-5` (so the small tier is pinned to the id `claude-haiku-5-5`, listed in Claude Code's model catalog; a live call could not be made from the machine used); VS Code was not run, it takes the qualified name from the list.

Each agent's `claude-tools` field is its tool allowlist in Claude Code (the generated `tools:`): without one, a subagent inherits every tool of the session, MCP servers included, and starts with all their schemas in context. In Claude Code the main conversation runs on the standard context window: `.claude/settings.json` pins `opus`, not `opus[1m]`. In the 1M window a factory run grew to 965k tokens before it compacted, and every turn read all of it again.

## Design

A ticket with a screen builds what the owner decided in the prototype. Before building or reviewing it, read the part of [`docs/design/prototype-v2/DECISIONS.md`](../design/prototype-v2/DECISIONS.md) for that surface, and the comments on the parent spec (`gh issue view <spec> --comments`): `issue.sh show` prints only the body, and the design decisions on specs approved before the prototype are in their comments. Where a ticket and `DECISIONS.md` disagree, stop and report it. `DECISIONS.md` §7 lists the prototype's assumptions: build the ones the owner confirmed, and ask about any other, don't build it as decided. The prototype shows look and flow, never architecture.

## Loop

1. `builder` builds the ticket and commits; it does **not** run `code-review`. `implement` ends with a `code-review` call; here that step belongs to the reviewer, so skip it.
2. `reviewer` reviews the head commit and reports its findings and the verdict, on the axes the review setting and the PR's risk ask for (**Review by risk**).
3. On must-fix or should-fix findings, a `builder` fixes them and the `reviewer` reviews the new head commit. At most two fix rounds (one for a `low`-risk PR, whose should-fix findings don't need a round: **Review by risk**); the review after the last is a **review-only round**: nothing more is fixed, and findings still open are listed in the notes file, so the PR stays for the owner (a `low`-risk PR with no must-fix finding left is clean).
4. The review is **clean** when the reviewer's last review, on the last commit, has no must-fix or should-fix finding; for a `low`-risk PR it is clean with no must-fix finding (**Review by risk**). Only the reviewer's verdict lets `work` record it with `pr.sh reviewed` (`--axes standards` when the verdict says `(standards)`); the builder never claims it.

### Review by risk (ADR-033 item 5, until pilot setup; ADR-034 sets the axes)

`.github/pipeline.json` says how a PR is reviewed, and `scripts/pipeline.sh get review` reads it. Both it and `scripts/risk.sh` decide, never judgment.

- **`per-pr`:** the reviewer runs both `code-review` axes (standards and spec) on every PR, as before ADR-034, and the verdict is `clean on <sha> (standards, spec)`.
- **`split`** (ADR-034, decision 4): a `low`-risk PR gets the **standards** axis only, plus the mechanical acceptance-criterion check (**Review**), and the verdict `clean on <sha> (standards)`; `pr.sh reviewed --axes standards` records it. A `high` or `owner` PR keeps both axes (verdict `(standards, spec)`, `pr.sh reviewed` without `--axes`), because a late spec finding costs most there. The spec axis then runs once per merged slice or ticket PR and once per spec (**Spec review**). `pr.sh reviewed --axes standards` and the merge gate refuse a standards-only record unless the setting is `split` and the PR is `low` (also when a later push made it high-risk); an unknown setting needs both axes.

The fix rounds stay as ADR-033 item 5 sets them, with either setting (below). `scripts/risk.sh` reads a PR. Until there is a PR the risk is unknown and the full rule applies: while a review has must-fix findings, a `builder` fixes them as usual (a fix round spent before the draft counts as the one low-risk round). Once a review has no must-fix finding left and there is no PR yet, `work` opens the draft with `pr.sh create` and reads the risk. With `split`, `work` opens the draft **before** the first review, so the risk and with it the axes are known and a `low`-risk PR is not reviewed on both axes first (the push costs one `check.sh --fast`). `work` notes a low-risk clean as `reviewed <sha> (<scope>): clean (low risk, <n> should-fix follow-ups)`, and a resumed run (`draft-pr`) accepts that line as the review of that head commit. With `split` the note names the axes of the verdict: `clean (standards)`, `clean (standards, spec)`, `clean (low risk, <n> should-fix follow-ups; standards)`; the resumed run records it with `pr.sh reviewed --axes standards` for `(standards)`, and without `--axes` for `(standards, spec)`.

- **`low` PR:** one `reviewer` pass (both axes with `per-pr`, standards with `split`) and at most **one** fix round. Only must-fix findings block it. The reviewer reports `not clean on <sha>` as usual, with the number of must-fix and should-fix findings; with no must-fix finding left on the last commit, `work` counts the review as clean and records it with `pr.sh reviewed --should-fix <n>`, plus `--axes standards` when the verdict says `(standards)` (`n` = the should-fix findings still open; the record says so, and `--axes` says which axes it covers). The should-fix findings still open go to the notes file as follow-ups (file, line, what to change), so the PR merges with them open. The review after the one fix round is review-only, as after the second round below.
- **`high` and `owner` PR:** as before: both axes, no must-fix or should-fix finding, up to two fix rounds. `pr.sh reviewed --should-fix` refuses these, and the merge gate refuses a record with should-fix findings left when the PR is not `low` (also when a later push made it high-risk).
- A review still needs a `reviewer` verdict, for every risk: `pr.sh merge` refuses a PR without one. A fix round that changed the risk (it touched a high-risk path) is reviewed under the rule of the new risk.
- The rule ends at pilot setup, with the other `@agent-queue` lines ([ADR-033](../decisions/ADR-033-go-live-mode.md)); from then on every review is full again.

A new commit makes an earlier verdict stale: any fix, CI repair or merge of `origin/main` is followed by a review on the new head commit before `pr.sh reviewed`, scoped to what changed since the last review (**Review**, Scope). A branch that is merely behind `origin/main` needs no merge: the merge queue tests the PR on the latest `main` ([ADR-018](../decisions/ADR-018-merge-queue.md)); merge `origin/main` only to resolve a real conflict.

After a clean verdict `work` records it with `pr.sh reviewed` (`--axes standards` for a standards-only verdict) and ships with `pr.sh ship`, then `pr.sh merge` adds a low-risk PR, and until pilot setup a high-risk PR that is not owner-only, to the merge queue (GitHub squash-merges it when the checks pass on the latest `main`; the owner queues an owner-only PR, [ADR-021](../decisions/ADR-021-agents-queue-high-risk.md)); how, including the follow-up pushes, is in the `work` skill's **Ship** section. A PR the queue removes for a cause in it comes back as a fix round: the brief names the failing checks of its `merge_group` run, and the same rules apply. When the cause is outside the PR, the bug filed for it is an ordinary ticket, built first; the PR is then queued again, once, with `pr.sh merge <pr> --after <bug>` ([ADR-025](../decisions/ADR-025-requeue-after-a-fix.md)).

## Build (the builder)

- **Read first**: `scripts/issue.sh show <n>` and its parent spec, the notes file, `AGENTS.md`, `CODING_STANDARDS.md`, `docs/agents/domain.md`, and the `.github/instructions/*.instructions.md` for the files you touch.
- **Stay in the worktree**: `cd <worktree> && …` in every command; change files only there.
- **A platform slice** (ADR-033, `scripts/flow.sh start --slice <spec> <platform>`): the brief names several tickets, up to 5, of one spec on one platform, in one worktree and one branch. Read every ticket and the spec first, build them one after the other in the order of the slice (a ticket blocked inside the slice comes after its blocker), each test-first against its own acceptance criteria, and commit each ticket on its own, with the feature ID of the ticket as scope. Apply every `Hint (#n)` it prints. Notes are one file for the slice: record each ticket in it. `pr.sh create` closes every ticket of the slice and warns above about 1,500 changed lines: when the work is going to pass that, finish the tickets that are done and report the rest as not built (name each ticket and why: blocked, or past the line limit), so `work` takes each out of the slice with `scripts/flow.sh slice <first> --drop <ticket>` before `pr.sh create` and leaves it for another slice; a ticket still in `.work/<first>/slice` is closed by the PR. Stop with `blocked` naming the ticket when one of them is ambiguous; the tickets before it are committed and stay in the report.
- **Acceptance criteria → tests** (the notes of every ticket, ADR-034; with `per-pr` too): under `## Acceptance criteria → tests (#<n>)` one line per acceptance criterion of the ticket, `AC <n>: <test file> › <test name>`, naming the test that proves it, as it is in the diff (a bug fix: the test that failed first). A criterion no test can prove (an owner or manual check) says `manual: <what was checked and how>`. The reviewer checks the list against the diff (**Review**). A slice has one list per ticket.
- **Tests**: `tdd`, one vertical slice at a time, covering the ticket's acceptance criteria and the spec's Test plan rows for them ([TESTING.md](../engineering/TESTING.md)). A fix for a finding or thread that changes behaviour starts with a failing test. Never delete, skip or weaken a test.
- **Native tests locally**: when `scripts/pipeline.sh get ci` says `fast` (ADR-034), CI runs the native unit tests only, so run the same locally: `scripts/test-ios.sh --unit-only` and `scripts/android.sh test --no-ui` (a UI test you changed or added is checked at night, on `main`; run it too when the ticket is about it). With `full`, or without the flags, the scripts run everything, as `pnpm test:ios` and `pnpm test:android` do.
- **Manual checks** (for the builder and for `work`, which records their results): steps for a manual or owner check, and the result recorded for one (in a PR body, notes or issue), prove the **data path**, not only the screen: change the row in a preview or test database and watch the screen change, or compare the endpoint's response with the row. A greeting that renders proves nothing while the endpoint is a stub (#59, #93).
- **Owner-only edits** (spec #292): `scripts/pr.sh create` prints the owner-only reasons of a ticket PR after it pushes (`scripts/risk.sh <pr>` shows all of them). An owner-only edit that the ticket does not need in the same commit does not ride along in the ticket PR: move it to a small PR of its own on a `chore/` branch (`scripts/flow.sh start` is for tickets; `scripts/wt.sh add chore/<slug>`), which nothing blocks and which only the owner queues, and note it in the notes file. The builder does not push or open it; the report names it so `work` does. When the ticket cannot work without the guarded change, that PR goes first and the ticket PR waits on it (say so in the report). A ticket PR that is owner-only only because of its issue's `owner-only` label has nothing to split.
- **Database migrations**: two PRs that each add one take the same number. When a merge of `origin/main` brings a migration (or `scripts/check.sh` fails on "database migrations"), merge `origin/main`, then run `node scripts/db-renumber.mjs` and `git add packages/database/migrations`. It moves your migrations after main's last (SQL files, journal entries, snapshot chain), keeps the SQL as it is, and refuses when the migration has already run in a local database you give it (`--database-url`; without it the script says it checked none, and a PR's own preview database is never checked: once the PR has deployed, its preview has run the old-numbered migration) or when main and you changed the same part of the schema. Never rename migration files, journal tags or snapshot ids by hand, and never delete and regenerate a migration to renumber it; when the script refuses, report it. Then run `pnpm test` in `packages/database` (the schema and snapshots must agree).
- **Parallel builders**: the factory runs up to 4 builders at once while the 1-minute load stays under about 50 ([ADR-033](../decisions/ADR-033-go-live-mode.md); it was 2 while local e2e runs and simulators drove the load up). Count only builder agents actually running; a PR that only waits on CI or on the owner doesn't count. Start the next ticket when fewer than 4 run and the load is under the limit, and don't kill running jobs to get under it.
- **Hint**: apply it. It says what this PR does to `FEATURES.md`: the spec's first ticket changes only its row's Status to `IN PROGRESS`, the PR that completes the spec sets `IMPLEMENTED` and writes the final one-line summary, any other ticket leaves the file alone. Never add progress ("Open:", "Next:") to the row; it lives in the spec's tickets.
- **Checks**: `scripts/check.sh` passes in the worktree. It runs only what the change can affect (the changed packages and their dependents, their integration tests, the web e2e tests when the web app is affected, the root script tests for scripts and hooks; Markdown only: the hygiene checks), the same set `pr.sh create` runs before every push, but without the integration and e2e tests (`pr.sh create` runs `check.sh --fast`, those two run only in CI, `--full` runs everything: [ADR-033](../decisions/ADR-033-go-live-mode.md)); the workspace setup (lockfile, root `package.json`, `turbo.json`, `tsconfig.base.json`, the shared test preset) affects everything. Run it per round and while you build (after each commit, only the tests the change can affect: one test file, `node --test scripts/test/<file>.test.mjs`, shellcheck on the script you touched). Use `--all` only when the round changed the workspace setup or the reviewer asks for the full run (modes: [WORKFLOW.md §3](../engineering/WORKFLOW.md), [ADR-024](../decisions/ADR-024-run-only-the-checks-a-change-can-affect.md)). At the end it prints a table of the tests each suite passed, failed and skipped, and writes it to `.work/check-summary.json` (git-ignored, in the worktree); a suite left out by `--fast` is listed as `skipped`, one the change does not affect as `skipped (not affected)`, one turbo never ran after a failure as `not-run`. **Quote that summary** in the notes and the report, rows as printed (`root                               pass                       351       0       0`: suite, status, passed, failed, skipped); never retype a count from the long test output. Native iOS and Android counts are not in it: `check.sh` doesn't run those suites.
- **Commits**: Conventional Commits with the feature ID as scope, `feat(F031): hold a spot during verification`. Commit everything before you report: the reviewer reviews only what is committed.
- **No final review**: don't call `code-review`; the `reviewer` does (see Review).
- **Never** push, create or update PRs, or write to GitHub issues. Never guess a product rule; test data is synthetic. Stop with `blocked` when the ticket is ambiguous, needs a product decision, or a check fails for reasons outside the ticket.
- **Notes**: append what you built, decisions, check results and anything left.
- **Report** in at most 10 lines: `done` or `blocked: <why>`, commits and the head SHA, checks with results (the counts quoted from `.work/check-summary.json`), open questions.

## Review (the reviewer)

The `reviewer` runs `.agents/skills/code-review/SKILL.md` in the worktree on the head commit; it never edits, commits or pushes.

- **Scope** comes from the brief; `work` sets it from the last verdict in the notes file. Each review covers only what no earlier review on this branch saw:
  - **`full`**, the first review of a branch: fixed point `origin/main`, the diff `origin/main...HEAD`.
  - **`since <sha>`**, every later review (after a fix round, a CI repair, a review-loop fix or a merge of `origin/main`), with the last review's must-fix and should-fix findings in the brief. First check `git merge-base --is-ancestor <sha> HEAD`; when it fails (history rewritten), review `full` instead. Otherwise walk `git rev-list --first-parent --reverse <sha>..HEAD`: review a merge of `origin/main` (`git merge-base --is-ancestor <merge>^2 origin/main` holds) by what its conflict resolution changed, `git show --remerge-diff <merge>` (empty when git merged it without a hand-made change), and any other commit, other merges included, by its own diff against its first parent. Check that each finding from the brief is resolved; one that isn't stays open. Read the surrounding code where a diff needs it; don't review the earlier commits again.
- **Axes** (**Review by risk**): `scripts/pipeline.sh get review` and the PR's risk (`scripts/risk.sh <pr>`) decide them, and the brief names them. The standards axis alone, with `split` and a `low`-risk PR, comes with one mechanical check instead of the spec axis: the notes file lists, under `## Acceptance criteria → tests (#<n>)` for every ticket in the PR, the test that proves each acceptance criterion, and the reviewer reads the ticket to see that no criterion is missing from the list and that each named test exists in the diff (`git diff origin/main...HEAD`, the test file and name). A criterion with no test and no `manual:` line, a missing list, or a test the diff does not contain is a `must-fix` finding. The spec itself is not read for the rest: that is the spec review.
- **Sources**: the spec is the ticket and its parent spec. Standards are `CODING_STANDARDS.md` (its checklist and the rules it links) and the instructions for the changed files; the skill's smell baseline applies under them. The spec axis also checks that the tests prove each acceptance criterion in NL and EN where the spec asks for both.
- **The axes in the reviewer itself**, one after the other: start no sub-agents for them. This replaces step 4 of `code-review`, which starts one per axis; each would start fresh and read the same diff and standards again.
- **Findings** are marked `must-fix`, `should-fix` or `judgement`, each with file, line and what to change.
- **Verdict**: the axes it covered, `clean on <sha> (standards)` or `clean on <sha> (standards, spec)`, when no must-fix or should-fix finding is left on that commit, otherwise `not clean on <sha>`; give the number of open must-fix and should-fix findings, because for a `low`-risk PR `work` counts a review with no must-fix finding as clean (**Review by risk**). It covers the whole branch: every commit was reviewed in some scope, and the findings of the last review are carried into this one.
- **Report** in at most 15 lines: the head SHA, the scope (`full` or `since <sha>`), the findings and the verdict. In a review-only round, report only what is still open.

## Spec review (ADR-034, with `review: split`)

With `per-pr`, the spec axis runs on every PR and this section does not apply. With `split`, a fresh `reviewer` checks what the PRs merged against the spec, per acceptance criterion, so a wrong reading of the spec is found after one slice, not after the whole spec.

- **When.** After each slice or ticket PR of a spec merges: `work` runs it right after `scripts/flow.sh finish`, on that PR's squash commit, for an issue that has a parent spec. And a **final** review when `flow.sh status <spec>` says `spec-review` (every ticket closed, no clean final review recorded that covers the last merged PR): it covers the whole spec across its platforms, the acceptance criteria no ticket owned, and the parity of iOS and Android. A spec in `spec-review` is ready work in `flow.sh next` (`Review spec #n`).
- **The map.** `scripts/spec-review.sh map <spec>` (`--json` too) rebuilds it from GitHub at any time: every acceptance criterion of the spec and of each sub-issue (tickets and bugs), the sub-issue that owns it, its state, the PR that closed it, that PR's squash commit and files. The brief names the spec, the PR and its commit (or `final`), and the map.
- **The review.** The `reviewer` reads the code at the SHA of `origin/main` named in the brief (`work` fetches it and names it; never a newer `origin/main`) and reports, for each acceptance criterion of the tickets that PR closed (final: of the spec and every ticket), `passes`, or `fails` with the file, the line, the commit and the ticket it traces to: `git blame` the line to its squash commit, `[F0xx] … (#PR)`, which closes its tickets in the map. It reports `clean` (every criterion passes) or `not clean` with the number of findings; it never files issues or records anything.
- **Findings** become **bug tickets under the spec**, filed by `work`: `scripts/issue.sh create bug --parent <spec> --label ready-for-agent --title … --body-file -`. The body starts with the line `Found by: spec review` (`scripts/usage.mjs` counts bugs by source from it), then names the acceptance criterion, the file and line, the commit, the PR and the ticket it traces to, what is wrong and what it should do, and has its own `## Acceptance criteria`. The bug is built through the normal lane (`flow.sh start`, builder, standards review, ship) and keeps the spec open: while it is open the spec is `building`; closed, the spec is `spec-review` again (or `complete`, once a clean final review is recorded that covers its merge).
- **Verdicts** are recorded with `scripts/spec-review.sh record <spec> (--slice <pr> | --final) clean|not-clean [--findings <n>] --sha <commit>`: a line in `.work/spec-<spec>/spec-review.md` of the main checkout (git-ignored) with the time, the scope, the verdict and the SHA the reviewer reviewed. `--sha` is required and is the commit of `origin/main` that `work` fetched and named in the brief before the review, not the `origin/main` of the moment it records the verdict: a PR that merged while the reviewer read is then not counted as reviewed. `scripts/spec-review.sh status <spec>` says whether a final clean review covers the spec's last merged PR, that is whether that PR's squash commit is an ancestor of, or equal to, the recorded SHA; `flow.sh` reads it for the phase. A PR that merges after a clean final review (a bug's fix) makes the spec `spec-review` again.
- **Never** more than the map's criteria: a finding with no acceptance criterion behind it is a `judgement` note in the report, not a bug ticket. If spec reviews often send work back across several tickets, the owner switches `review` back to `per-pr` (ADR-034, decision 5).

## Fix rounds (the builder again)

A `builder` gets the reviewer's must-fix and should-fix findings (for a `low`-risk PR only the must-fix ones; its should-fix findings go to the notes file instead, **Review by risk**; or the failing checks of a `merge_group` run, when the merge queue removed the PR) in its brief (judgement findings are optional), fixes them test-first when behaviour changes, runs `scripts/check.sh`, commits and reports as above. Never delete, skip or weaken a test to make a finding go away.

## Usage

`node scripts/usage.mjs snapshot --since <date> [--until <date>] --label <name>` measures a run from Claude Code's transcripts on this machine: tokens, price-weighted cost per model, agent and tool time per ticket, and quality (first-review-clean rate, findings per review, CI failures, queue removals, owner comments, follow-up fixes, reverts). `node scripts/usage.mjs compare <before.json> <after.json>` compares two snapshots per ticket group (area and size), so a run is compared with runs of similar tickets, not with a different mix. Claude Code deletes transcripts after 30 days by default, so take the snapshot within that time. Baselines live in `docs/agents/usage/`; `2026-10-24-factory.json` is the run before the review, tools and context-window changes, and `2026-11-18-full-pipeline.json` the last four weeks of the full pipeline, before ADR-034 (the baseline a factory run compares with).

**The flow of the delivery** (ADR-034). A snapshot also has a `flow` section, read from GitHub for the same window (the 28 days before `--until` without `--since`); it is `null`, with a warning, without `gh`. It holds:

- `settings`: the `.github/pipeline.json` values (`ci`, `review`) on `main` at the window's start and end, read with `git show` (a missing file is `full` and `per-pr`), so a snapshot says which flow it measured. When they changed inside the window the snapshot and `compare` warn that the numbers mix both.
- `time`: for the merged PRs, in hours (median and p90): issue opened → first commit (the backlog), first commit → PR opened, PR opened → ready for review, ready → first queued, first queued → merged, PR opened → merged and issue opened → merged; the tickets merged per day; and, for the specs closed in the window, created → `spec-approved` → first ticket → closed.
- `ci`: the runs of `ci.yml` per event (`pull_request`, `merge_group`, `push`, `schedule`: count, wall time, failure rate), per job (median run time and failure rate; the nightly run apart, as `<job> (schedule)`), the runner hours on Linux and macOS, the runs per merged PR and the queue removals per PR by reason (`failed_checks`, `merge_conflict`, `checks_timed_out`, ...). The jobs of a run cost one call each: they are read eight at a time and kept per run id in `.work/usage/jobs/`, so a second snapshot is cheap.
- `quality`: the issues labelled `bug` opened in the window, by source (`nightly`: the title `Nightly UI tests failed`; `specReview`: the body line `Found by: spec review`, which the spec review puts in a bug it files under a spec; `deploy`: the marker `flow.sh` puts in a `Deploy bug:`; `other`: the owner or anyone else), the bugs per merged ticket, the reverts, the follow-up fixes and the PRs merged with should-fix follow-ups (the `pr.sh reviewed --should-fix` record). The first-review-clean rate and the reviews per ticket stay in the per-ticket metrics.
- `prs`: one record of numbers per merged PR, so `compare` also shows the times per ticket group (area and size).

Only numbers, issue and PR numbers, SHAs, job names and labels are written: no title or text of an issue or PR is stored.

**Comparing the full and the fast pipeline.** `2026-11-18-full-pipeline.json` is the full flow (tag `pipeline-full-2026-11-18`, `ci: full`, `review: per-pr`), 21 October to 18 November. After the switch, from the day it merged:

```
node scripts/usage.mjs snapshot --since <switch date> --label <date>-fast-pipeline
node scripts/usage.mjs compare docs/agents/usage/2026-11-18-full-pipeline.json docs/agents/usage/<date>-fast-pipeline.json
```

Take the second snapshot within 30 days of its window (the transcripts). A fair comparison needs at least a week, or about 50 merged tickets, on each side, and is read per group: the overall numbers move with the mix of native, app, tooling and docs tickets, and a group marked `(few)` has fewer than 3 tickets on one side. Switching back and forth inside a window mixes both flows (the warning above): take one snapshot per stretch of one setting. The nightly bugs belong to the fast flow's cost: read the bugs per merged ticket together with the time, not apart.
