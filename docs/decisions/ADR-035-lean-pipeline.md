## Context

The owner, on 19 November 2026: "Fast check on the laptop. Development 1 job at a time, so no more conflicts. GitHub runs the e2e tests and integration tests once at night. We go fast till the apps are ready."

- **Parallel PRs conflict.** With up to 4 builders each ticket is built on the `main` of the moment it started, and PRs that touch the same files, generated files, lists and tables conflict when the first one merges. A merge conflict costs a refresh or a fix round and a second run through CI and the queue (the Refresh step of `flow.sh next` exists for it, #1274).
- **Time in CI.** `Checks (Linux)` runs `lint typecheck test test:integration build format:check check` in one turbo run. Measured on the runs of the last days, a change to a package almost every other one depends on misses the turbo cache everywhere and the job takes 11 to 16 minutes uncached, the integration tests (Postgres service container) included. The job is on every PR's path twice: on the PR and in the merge queue.
- **The queue removals of the last days were not failing tests of the PR.** They were job timeouts (E002 #1490: the merge group was cancelled at the old 15 minutes with no test failing) and one clock-dependent flaky integration test (#1494). Each removal costs a fix round and a second queue run.
- **The merge queue does nothing with one PR in flight.** It builds the PR on the latest `main` and runs CI again, which is the same code the PR's own run just tested (the PR was built on a `main` that had the previous PR), and every queue run costs minutes and can remove a PR for a timeout or a flaky test with no change in the code.
- ADR-034 already moved the UI tests to the nightly run, and the builders already run the local check in its `--fast` form (`scripts/check.sh --fast`: hygiene, lint, types, unit tests, static checks, build; no integration, no e2e).

## Decision

1. **`ci: lean`.** Everything `ci: fast` does (ADR-034: no UI tests on a PR, a merge group or a push; they run at night), and the **integration tests** (`test:integration`) leave `Checks (Linux)` on `pull_request`, `merge_group` and `push` as well. They run in the nightly run (`schedule`) and on `workflow_dispatch`, like the UI tests. The rule lives in one place, `scripts/pipeline.sh integration-tests --event <event>` (`true` for `full` and `fast` on every event, for `lean` only on `schedule` and `workflow_dispatch`); `Detect changes` asks it and outputs `integration_tests`, and `Checks (Linux)`, which now waits for `Detect changes`, adds `test:integration` to its one turbo run only unless the output says `false`. The required check names do not change. The merge queue still guards `main` with lint, types, unit tests, the build, the format check and the static checks (i18n parity, contract drift and so on).
2. **`builders: 1`.** A new setting, a positive integer, `scripts/pipeline.sh get builders` (fails closed like the others): the most tickets or slices the factory has in flight at once. With 1, the next ticket or slice starts only after the previous PR merged, so it is built on a `main` that has it and the PRs do not conflict; while the PR is in review, in CI or in the merge queue, the factory waits for it and starts no other builder. A PR that waits on the owner (owner-only, refused by the merge gate, `ready-for-human`) does not hold the next ticket back, since that can take long. Spec reviews, the `reviewer` and the `mechanic` do not count as builders. The `work` skill and `docs/agents/build.md` read the number instead of the fixed "up to 4 while the load stays under about 50" (ADR-033), which stays the rule for a number above 1.
3. **The local check is the fast check.** Every rule that says "while `ci` is `fast`" also covers `lean`: builders run `scripts/check.sh --fast` and the native unit-only modes. Because nothing else runs the integration tests before the merge, the builder runs the integration test files of what the ticket touches itself (`docs/agents/build.md`, **Checks**).
4. **The nightly report names the failing suite.** The issue `Nightly UI tests failed` (the title stays: `flow.sh`, `usage.mjs` and the factory match it) says which suites failed: `Integration tests and the other Linux checks` (`Checks (Linux)`), `UI tests and native jobs`, or `Detect changes`. The job's log says which turbo task failed. `flow.sh` lists the nightly bug first with `lean` as with `fast`.
5. **No merge queue while lean: `merge: direct`.** A fourth setting, `merge` (`queue`, ADR-018, or `direct`; `scripts/pipeline.sh get merge`, fails closed). With `direct` the ruleset on `main` has no `merge_queue` rule and its required status checks are strict (`strict_required_status_checks_policy: true`: the branch must be up to date with `main`), squash only, the same five required checks, no bypass. There is one ruleset file, `.github/rulesets/main.json`, which stays the queue form; `scripts/github-settings.sh apply` derives the direct form from it (drops the `merge_queue` rule, sets the strict policy), so there is one source. `pr.sh merge` runs the same whole merge gate, then squash-merges with `gh pr merge --squash --match-head-commit` (the path it already had for a branch without a queue); when GitHub refuses because the PR is behind `main` it says so and points to the Refresh steps of the `work` skill (merge `origin/main`, check, review the merge, push, wait for CI, merge again). When the setting and GitHub disagree (the owner has not applied the ruleset yet) it prints a one-line warning and goes by what GitHub has. `pr.sh merge --after` (ADR-025, the re-queue after a fix) refuses with `direct`: there is no queue to re-queue in. With `builders: 1` the next ticket starts right after the previous PR merged, with no queue wait. **The owner applies the ruleset after the PR merges**, from the main checkout, with the owner's admin token: `git switch main && git pull && scripts/github-settings.sh apply` (it prints `ruleset 'main' updated (merge: direct)`; `WORKFLOW.md §8` has the steps).
6. **Going back** is `WORKFLOW.md §8`: `ci: fast`, `builders: 4` and `merge: queue` (then `scripts/github-settings.sh apply` again) is the setup at the tag `pre-fast`; `ci: full` is the setup at `pipeline-full-2026-11-18`. `scripts/usage.mjs` records `builders` with the other settings, so `compare` shows the flow before and after.

## Consequences

- **Integration bugs reach `main` and show up the next morning.** Tenant scoping, authorization, the database and API routes against real Postgres are tested by the integration suites; with `lean` a regression there is found by the nightly run, opens the nightly bug, and the factory builds that bug before any other ticket. Between the merge and the next morning, `main` and the development deployment can hold it. The reviewer's standards axis, the unit tests and the builder's own run of the touched integration files are the defence before.
- **The merge queue is shorter and steadier**: `Checks (Linux)` loses its slowest tasks on every PR and again in the queue, and the flaky or clock-dependent integration tests (#1494) can no longer remove a PR from the queue. The job timeout stays at 25 minutes: the nightly run still needs it for a full uncached run.
- **Throughput is lower per day, and each ticket is faster to land**: one ticket at a time trades the 4 parallel builders for no conflicts, no Refresh rounds and no queue removals by conflict. The factory idles while one PR waits for CI and the queue; `builders` is the knob if the owner wants it back.
- **Before pilot setup `ci` goes back to `fast` or `full`.** When real personal data enters production, the integration tests (tenant scoping, auth, the database) must gate every merge again. T12 of the processor agreement promises the required CI checks of the merge queue; with `lean` those checks still run under the same names, and the claim stays true, but the integration tests are no longer among them, which is not acceptable once clients' data is in the system. `builders` may stay at 1. The owner does this in one PR (`WORKFLOW.md §8`), and it is a step of the pilot setup.
- **The nightly run carries more**: the integration tests join the UI tests in the nightly run, and `Nightly report` already needs `Checks (Linux)`, so a failing night opens or updates the one issue. Two failures on one night (a UI test and an integration test) are one issue with two suites in it.
- **A PR that touches the migration or the database** is checked by the unit tests and the static checks only before the merge; a migration that does not apply is found by the nightly run. The `Quarantine` job, which is not required and never fails, still runs the listed integration tests on every run.
- **A PR that is behind `main` must merge `main` in and run CI again before it merges.** With strict required checks GitHub refuses the merge of a branch that is not up to date. With one PR at a time this happens only when something else reached `main` meanwhile (an owner PR, a chore): the Refresh steps cover it, at the cost of a review of the merge and a CI run. The queue's guarantee that every merge was tested on the latest `main` is replaced by the same guarantee through the strict policy, without the queue's second run.
- **No re-queue after a fix** (ADR-025): without a queue nothing is removed; a failing check is fixed in the PR or by its own bug, and `pr.sh merge` is run again.
- **The queue comes back** with `pre-fast` (`merge: queue`, then `github-settings.sh apply`), or before pilot setup if the owner wants the queue's re-test again. `ci` must leave `lean` then anyway.
- **Between the merge of this change and the owner's `github-settings.sh apply`** GitHub still has the queue: `pr.sh merge` warns and queues as before.
- **Nothing is deleted**: the integration test jobs and scripts, the full and fast modes and the docs of both stay, behind the switch.

## Alternatives considered

- **Keep the integration tests on every PR and only serialise the builders.** Removes the conflicts, but keeps the 11 to 16 minutes in CI twice per PR, which the owner wants gone while the apps are not ready.
- **Run the integration tests on a PR only when the API, the database or auth changed (path filtering).** Cheaper than all or nothing, but a second decision on top of `scripts/affected.mjs`, and a missed dependency becomes a silent hole; the nightly run is simpler and complete.
- **Make the integration tests a second job that is not required.** Keeps their feedback on the PR, but takes the same runner minutes, and a red check that nobody has to act on is ignored. The nightly bug is acted on first.
- **Keep the merge queue with one PR at a time.** Still correct, and it re-tests on the latest `main`, but with one PR in flight the latest `main` is what the PR was built on, so it costs a full CI run (and a possible timeout or flaky removal) for no new information; the strict policy covers the rare PR that is behind.
- **Stay with 4 builders and fix the conflicts with the Refresh step.** That is the setup before this ADR; conflicts still cost a round each, and the owner asked for no more of them.
