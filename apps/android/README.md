# Fivvi Pro and Fivvi for Android

Two native Android apps in one Gradle build (E008, E017, ADR-003): Kotlin, Jetpack Compose and Material 3 Expressive, Android 8.0 (API 26) and up. **Fivvi Pro** (`app/`, `app.fivvi.pro`) is for owners and trainers; **Fivvi** (`client/`, `app.fivvi`) is the client app, with the sign-in, the tabs *Home · Boeken · Profiel* and *Profiel*. Both are built on `core/`. Fivvi Pro opens on the sign-in (TM-01, F001: the email step, then the code from the email) and, signed in, on the home: the workspace name with *Klanten* and *Profiel* (F002, F003, F006, F012), the *Hello* block that proved every layer is connected (E008; it goes with #652) and the signed-in address. Its sign-in, home, *Profiel* and *Klanten* are on the v2 kit (E020, [Rules](#rules): *Theme*, *The kit*, *Screens in v2*). Fivvi opens on the same sign-in (it shows the name *Fivvi*) and, signed in, on the tabs.

## Run it

```bash
scripts/bootstrap.sh --mobile   # once: JDK, Android SDK, the `fivvi` emulator, Maestro
pnpm test:android               # what CI runs, in one go: ktlint, the release Sentry DSN, build (android.sh build), unit tests, Compose UI tests (android.sh verify)
pnpm test:maestro               # the local stack + e2e/maestro flows on the emulator, in nl-NL and en
                                # (CI builds the app once with android.sh maestro-apk and runs maestro.sh android --apk)
scripts/android.sh emulator     # boot the emulator and leave it running for repeated runs
```

The scripts give the emulator `EMULATOR_BOOT_TIMEOUT` seconds to boot (default 300). If it exits or doesn't boot in time, they fail with the end of `build/emulator.log` and the emulator's acceleration check. Every boot is cold on your machine. On CI (`AVD_SNAPSHOT=1`) the first cold boot saves a snapshot of the booted emulator, the AVD with it is cached, and later runs load the snapshot in seconds; a snapshot that doesn't load within `SNAPSHOT_BOOT_TIMEOUT` seconds (default 90) is deleted and the emulator boots cold. `scripts/android.sh avd-key` prints what the cache is keyed by.

To try an app against your local web server (`pnpm dev`, port 3000), run `./gradlew :app:installDebug` (Fivvi Pro) or `./gradlew :client:installDebug` (Fivvi) from this folder with the emulator running; both can be installed side by side. Commands are in `TESTING.md §7.1`.

| | Fivvi Pro | Fivvi |
|---|---|---|
| Module, application ID | `:app`, `app.fivvi.pro` | `:client`, `app.fivvi` |
| Build and run | `./gradlew :app:installDebug` | `./gradlew :client:installDebug` |
| Unit tests (nl-NL and en) | `./gradlew :app:testDebugUnitTest` | `./gradlew :client:testDebugUnitTest` |
| Compose UI tests (emulator) | `./gradlew :app:connectedDebugAndroidTest` | `./gradlew :client:connectedDebugAndroidTest` |

`:core:testDebugUnitTest` runs the tests of the shared code. `pnpm test:android` (`scripts/android.sh test`) runs all of them, for both apps. The Maestro flows (`pnpm test:maestro`) drive Fivvi Pro; the Fivvi flow (`e2e/maestro/fivvi/sign-in.yaml`) is ticket #507.

**What goes where.** `app/` and `client/` depend on `core/`, `core/` on `api/` and `design-tokens/` (it passes them on as `api` dependencies), and nothing depends on an app module. Code goes into `core/` when more than one Android app needs it (the sign-in flow, the session, the language, the theme, the shared load states, crash reporting, the strings); a screen, a view model or a rule of one product (Fivvi Pro's home, clients and Profiel; Fivvi's tabs and Profiel) stays in its app. Each app module owns its manifest, its application ID, icon and label, its build types and the wiring of `MainActivity`; `core/` has no application ID, no icon and a manifest without content, and reads nothing from `BuildConfig`: the app hands it what it needs (`Observability.start(context, observabilityConfigOfThisBuild())`, `ApiServices(BuildConfig.API_BASE_URL, session)`). Package names follow the module: `app.fivvi.core.*` and `app.fivvi.pro.*`. The version, the build number, the base URL and Sentry DSN per build type and the release checks (`checkReleaseApiBaseUrl`, `checkReleaseSentryDsn`, `checkNoAnalyticsSdk`) are written once in `gradle/app-build.gradle.kts`, which the root `build.gradle.kts` applies to both app modules (a module script that calls `apply(from = ...)` makes Android lint crash in the release bundle); `checkNoAnalyticsSdk` sees what `core/` brings. The release signing and the store lane of Fivvi come with its release-lane ticket (E017). ktlint (`ktlintCheck`) and its rules run on every module.

## Rules

- **Strings** come only from `packages/i18n`: `core/` includes `packages/i18n/generated/android` in place (`values/` is nl-NL, `values-en/` English), and an app reaches them as `app.fivvi.core.R`, with no copy in the app. The app label is `app.name`. `ktlintCheck` fails on a string literal in a Compose `Text` and names the file and line, in `core/` and `app/` alike.
- **Language** (ADR-017, spec #34, F010 spec #175): `AppLanguage.resolve` takes the explicit choice made on this device, then the account's stored preference (`GET /api/v1/me`), then the OS per-app language (API 33+, offered for `nl` and `en` by `res/xml/locales_config.xml`), then the first supported device language in order, then English; its cases are tested under the names of the TypeScript resolver (`AC6_explicit_…`, `AC6_stored_…`, `AC6_device_…`, `AC6_english_…`, `AC6_signOut_…`). `LanguagePreference` keeps the choice, the stored preference and whether the choice is saved on the device (`SharedPreferences`, no secret) and sets every change as the platform's per-app language (`LocaleManager`, API 33+; no AppCompat dependency), so the in-app choice and Android's setting are one; a per-app language set in Android settings that is not the language shown counts as a new choice. `LanguageViewModel` saves a choice with `PATCH /api/v1/me` (`preferredLocale`) and, when `GET /api/v1/me` answers (at sign-in and on every foreground), saves a choice the account does not have yet (made on the sign-in screen, AC5) or else adopts the stored preference and drops the older local choice (AC2). `MainActivity` gives the screens a context that follows the language, so a switch re-renders in place, without a restart, and the view models (and what was typed) stay. Android's own resource match is never the input: the default resources are Dutch. `PATCH /api/v1/me` carries `surface: android`, so the API records `language_changed` with that surface (a request with a token and no surface records nothing).
- **API** through the generated `app.fivvi.api` client only. The view models depend on the generated per-tag interfaces (`HelloApi`, `SignInApi`, `MeApi`, `WorkspacesApi`, `TrainersApi`, `ClientsApi`), which tests replace with `FakeHelloApi`, `FakeSignInApi`, `FakeMeApi`, `FakeWorkspacesApi` `FakeTrainersApi` and `FakeClientsApi` (`app/src/testShared`; `FakeSignInApi` and `FakeMeApi` are in `core/src/testShared`). The app has no hand-written API call or model; its one OkHttp client carries `AuthInterceptor` and nothing that logs.
- **Since the Fivvi rename (21 October 2026)** the Gradle properties are `fivvi.*`: rename any `trainerhub.*` in `~/.gradle/gradle.properties` or your `-P` flags, and delete the old `trainer-hub` AVD and `~/.config/trainer-hub` (the scripts create `fivvi` and `~/.config/fivvi`).
- **Base URL** per build type, from `gradle.properties`: debug `fivvi.apiBaseUrl` (the local server as `10.0.2.2` from the emulator; override with `-Pfivvi.apiBaseUrl=https://<preview>/api/`), release `fivvi.releaseApiBaseUrl`, the production API (`ENVIRONMENTS.md`, *Production address*): `checkReleaseApiBaseUrl` fails `pnpm test:android` and every release build on an empty, plain-HTTP or `.invalid` address or one that is not mounted at `/api`, and `pnpm test:android` shows that it does. Plain HTTP is allowed only in debug (`src/debug`, network security config).
- **Identifiers and version** (E017): application ID `app.fivvi.pro` (final: it can't change after the first upload to Google Play; `scripts/test/app-ids.test.mjs` (`pnpm test:root`) checks that the project uses the ID recorded here, `BuildInfoTest` that the build has it). `versionName` is the one version of both apps in [`apps/Version.xcconfig`](../Version.xcconfig); `versionCode` is the build number, `-Pfivvi.buildNumber=<n>` from a release run and 1 without it (debug builds, CI); `pnpm test:android` runs `BuildInfoTest` a second time with `-Pfivvi.buildNumber=42` to show that a number from outside becomes `BuildConfig.VERSION_CODE`.
- **Fivvi's identifiers** (E017 #504): the client app's own ID, `app.fivvi` (final, as Fivvi Pro's; `scripts/test/app-ids.test.mjs` checks it) and its label *Fivvi* (`app.title`, `AppLabelTest`). It reads the same `apps/Version.xcconfig` version and the same build number (`BuildInfoTest` in each app). Both apps report to the Sentry project `android`; Fivvi's events carry the tags `app: fivvi` (Fivvi Pro's: `app: fivvi-pro`) and `platform: android`, and no other tag (`ObservabilityAppTagTest`; OBSERVABILITY.md §1 "Android").
- **App icon** (E017, E020): the adaptive icon in `app/src/main/res` (background, foreground and the monochrome layer for themed icons) and `app/src/main/ic_launcher-playstore.png` (512 px) are generated, never edited: `pnpm app-icon`, see [`scripts/app-icon.mjs`](../../scripts/app-icon.mjs): the day dial B2 (the owner's choice of 8 November 2026): the light gradient as the background, the track and the five sectors (each with its pink gradient) as the foreground, the monochrome layer the two as one shape, everything inside the 66 dp safe zone. The five sectors' path data is copied unchanged from `docs/design/brand/day-dial/b2/layers/3-five.svg` into the script (reading the brand folder would make it an input of the cached root tests in `turbo.json`); the colours are the logo's own, not design tokens. Fivvi's (`client/src/main/res`, `client/src/main/ic_launcher-playstore.png`) is the plain day dial B2 as well (the owner's choice of 8 November 2026; Fivvi Pro gets B2 with PRO on top later, #672), written by the same script, never drawn by hand.
- **Sign-in session** (F001, AC11): the bearer token is kept only by `KeystoreSessionStore`: AES-GCM with a key from the Android Keystore, in `filesDir/session`, which `res/xml/backup_rules.xml` and `data_extraction_rules.xml` exclude from Auto Backup and device-to-device transfer (`BackupRulesTest`). Never `SharedPreferences` or plain text, and no Jetpack Security library (a new dependency needs the owner's approval). A file that can't be decrypted reads as no token. App start: no token is the sign-in screen with no authenticated call; a token is the home. `SessionStoreTest` runs on the emulator. A 401 to a request that carried the stored token deletes it and shows the sign-in with the signed-out notice; a late 401 for an older token changes nothing. Sign out (AC10) deletes the token first, then sends `signOut` through the generated client with a copy of it (`ApiServices.signOutApi`), waits at most 10 s (the clock of the coroutine dispatcher, virtual time in tests) and shows the sign-in, also offline; a 401 to that call shows the notice. The code field takes a paste and the phone's one-time-code autofill (`ContentType.SmsOtpCode`) and checks as soon as six digits are in.

- **Capabilities** (F004 AC9, AC10): `capabilities/WorkspaceCapabilities` is the one helper that answers "may I show this action here?": `mayShow(workspaceId, capability)` is true only when `GET /api/v1/me` lists the capability (the generated `MeWorkspace.Capabilities`) for that workspace. Nothing else in the app decides it and nothing tests the role name; the role is only the label on *Profiel*. It is filled by the answer the home reads on opening (`HomeViewModel.onWorkspaces`) and by the one on foreground (`LanguageViewModel.refresh`, which already reads `/me` then: no extra request); until the first answer, and for a workspace the API doesn't list, nothing shows. *Profiel* shows an *I also train here* switch in a workspace only when `GET /api/v1/me/workspaces` lists `team.manage` there (`MyWorkspace.capabilities`, the same list), never from the role. A call that a capability guards passes its answer to `onResponse(response, workspaceId, capability)`: a 403 hides the action at once and reads `/me` again. F006 (M4) uses it: the *Klanten* button on the home shows from `clients.view`, and *+ Nieuwe klant* and *Bewerken* from `clients.manage`; a 403 or 404 from the clients routes goes to `onResponse`. The iOS helper reads the same source.
- **Theme** (ADR-015, ADR-029, E020): wrap screens in `FivviTheme`. It is Material 3 Expressive (`MaterialExpressiveTheme` with Expressive's motion): the generated `LightColorScheme` or `DarkColorScheme` as the system's mode is, and `TokenShapes`. No dynamic colour (Material You). Text is **Google Sans Flex** in Material 3's type scale (`FivviTypography`): use `MaterialTheme.typography` with the token names (`title1`, `body`), never a font size, so the system's font scale applies. **Numbers** on their own (times, weights) take `.numeric()` on their style: Google Sans Flex's round axis (`ROND` 100) with tabular digits (`tnum`); a count inside words (*Vol 3/8*) takes `.tabular()`, the digits alone. The generated `Typography.numericXl` is only the role (`displaySmall`; its note says "+ tnum"): use `numericXl.numeric()`. Colours come from `MaterialTheme.colorScheme`; for what Material doesn't cover (sessions, status), from `MaterialTheme.tokens` (`FivviTheme` provides the token colours of the same mode, so screens don't each pick the mode). Spacing comes from `Spacing`. `ktlintCheck` fails on a hard-coded colour (`Color(…)`, `Color.Red`, `colorResource`, Material's own or dynamic colour schemes) and names the file and line. The Material error colour is `status.danger.fg`.
- **Material 3 version** (AC9): `material3` is on the `1.5.0-rc01` release candidate, and only it: the rest of Compose stays on the BOM, because the catalog (`gradle/libs.versions.toml`) gives that one library its own version. Take the stable 1.5 release once it ships by changing `compose-material3` there, nothing else. `Material3PinTest` fails if the pin or its comment goes.
- **Google Sans Flex** (AC10): the one variable font `core/src/main/res/font/google_sans_flex.ttf` ships inside the app (no downloadable font, so no request goes to Google), under the SIL Open Font License 1.1; the licence is `core/src/main/assets/licenses/google-sans-flex-OFL.txt`, so it is in the repo and in the APK. The file is Google Fonts' `GoogleSansFlex[ROND,opsz,slnt,wdth,wght].ttf` (github.com/google/fonts, `ofl/googlesansflex`) with `fonttools` (`python -I -m fontTools.varLib.instancer GoogleSansFlex.ttf wdth=100 slnt=0 opsz=18 wght=300:800`, then `python -I -m fontTools.subset` to Basic Latin, Latin-1, Latin Extended-A, general punctuation, `€`, `−` with `kern,liga,calt,ccmp,locl,tnum,pnum,lnum,zero,mark,mkmk`, no hinting): two axes, weight 300 to 800 and round 0 to 100, 169 KB instead of 3.7 MB. A new character set or axis means doing that again from the upstream file. `GoogleSansFlexTest` reads the file's axes and the licence.

## Behind a company proxy

Some TLS-inspecting proxies (e.g. Zscaler) break Java downloads. The scripts handle the two cases seen so far:

- Java doesn't trust the proxy's CA: on macOS, `scripts/_android.sh` builds `~/.config/fivvi/java-cacerts` from the JDK's CAs plus the System keychain and sets `JAVA_TOOL_OPTIONS` for its own commands. Run Gradle through the scripts, or set the same option yourself.
- The proxy blocks jars on `repo.maven.apache.org`: `settings.gradle.kts` uses Maven Central's `repo1.maven.org` host instead.

## Releasing

Builds for testers go through Play internal testing; how a run is started and approved, how testers are added and what to do when an upload is rejected is in [`docs/engineering/RELEASE.md`](../../docs/engineering/RELEASE.md). The Android job of the release workflow (`scripts/release-android.sh`) builds the signed App Bundle with `./gradlew :app:bundleRelease -Pfivvi.buildNumber=<n>`; the release build is signed only when the environment names the upload keystore (`ANDROID_UPLOAD_KEYSTORE_FILE`, `ANDROID_UPLOAD_KEYSTORE_PASSWORD`, `ANDROID_UPLOAD_KEY_ALIAS`, `ANDROID_UPLOAD_KEY_PASSWORD`), otherwise the bundle is unsigned, and `pnpm test:android` checks the signing with a throwaway key.
