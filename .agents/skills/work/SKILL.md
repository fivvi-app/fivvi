# Work

You route; Matt Pocock's vendored skills do the work. Run every script, skill and subagent yourself, in order. Never ask the user to run a command or to remember the next step.

## Rules

- **Facts come from scripts, not memory.** Before acting on an issue run `scripts/flow.sh status <n>` and act on its `Phase`, `Next` and `Hint`. Run it again after each step instead of assuming what changed.
- **Claims need evidence.** Before you record a manual or owner check result, or write a status claim in `FEATURES.md`, `ROADMAP.md` or on an issue, check it against the code and the data path: `docs/agents/build.md`, **Manual checks**.
- **GitHub holds what was agreed:** specs, tickets, blocking edges, labels, assignees and PRs. Comment on an issue only when the owner must answer or act. Never post progress, logs or check results there.
- **Working memory is the ticket's notes file** (`flow.sh start` and `status` print its path): decisions, check results, what's left. Update it at every phase change so a fresh session can continue from `flow.sh status`, the notes, git and the PR. Keep no other plan or state files.
- **Run a vendored skill by reading `.agents/skills/<name>/SKILL.md` and following it.** Most are user-invoked only, so you can't load them as tools. Their tracker and docs steps resolve through `docs/agents/`.
- **Keep this conversation lean.** Each ticket is built by a fresh `builder` subagent and reviewed by a fresh `reviewer`; keep only issue numbers, phases and short reports here.
- **This conversation runs on the high tier** (models per tool: `docs/agents/build.md`, **Tiers**): shaping (grill, to-spec, to-tickets, triage) happens here, in the main conversation. You start the work on its tier as a subagent: `builder` (mid) builds and fixes, `reviewer` (high) does every code review, `mechanic` (small) does the mechanical work (**Subagents**, `docs/agents/build.md`). If this conversation runs on another tier, say so once and carry on; never run a review or a build here in its place.
- **The owner approves specs and adds owner-only PRs to the merge queue** (`docs/decisions/ADR-016-agent-merges.md`, `docs/decisions/ADR-018-merge-queue.md`, `docs/decisions/ADR-021-agents-queue-high-risk.md`, `docs/decisions/ADR-023-owner-out-of-the-per-pr-loop.md`). With `scripts/pipeline.sh get merge` = `direct` ([ADR-035](../../../docs/decisions/ADR-035-lean-pipeline.md)) there is no merge queue: the owner merges an owner-only PR on GitHub, and `pr.sh merge` squash-merges the others itself. Until pilot setup you also add a high-risk PR to the queue (or, with `direct`, squash-merge it) when it is not owner-only: low and high risk alike go through `scripts/pr.sh merge` only; it decides, not you, and it records a high-risk merge in the PR body. Never approve a PR, merge in any other way (no `gh pr merge` by hand, no `--admin`), or enable auto-merge (`--auto`). Agent review stays local (`docs/engineering/WORKFLOW.md §4`).
- Keep going while the next phase doesn't need the owner. Stop and report when it waits on a human: a spec approval, a product decision, an owner-only PR, a PR the merge gate refused or a PR the merge queue removed.

## Phase playbook

| Phase | Do |
|---|---|
| `needs-spec` | **Shape** on this issue; publish with `scripts/issue.sh update <n>` instead of creating a new one. Keep its intent and show the new body before writing. |
| `needs-approval` | Report and stop: the owner approves the spec on GitHub with the `spec-approved` label. |
| `needs-tickets` | **Shape** from step 3. If one PR is enough, add `## Acceptance criteria` and the `ready-for-agent` label to the spec itself. Adding ACs is a material change: `issue.sh update` removes `spec-approved`, so the spec waits for the owner to approve it again (`needs-approval`); report and stop, and **Build** it as a ticket once approved. Use `--minor` only for edits that change nothing material. |
| `building` | **Build** the ready tickets, at most `scripts/pipeline.sh get builders` at once ([ADR-035](../../../docs/decisions/ADR-035-lean-pipeline.md): with 1, one ticket or slice in flight, the next one starts after the previous PR merged; with more, also while the 1-minute load stays under about 50, [ADR-033](../../../docs/decisions/ADR-033-go-live-mode.md), and no more agents at once than the tool's rate limits allow, and tickets that change the same files one after the other; `docs/agents/build.md`, **Parallel builders**); `triage` tickets that aren't `ready-for-agent`, one at a time with the user. |
| `needs-refinement`, `answered` | `.agents/skills/triage/SKILL.md` on it, one at a time with the user. |
| `waiting` | Report and stop: the owner answers the `needs-info` question on the issue. |
| `ready`, `in-progress` | **Build** (for `in-progress`, resume from the notes file and the worktree's commits) |
| `draft-pr` | **Ship** from step 2; if the notes file has neither `clean on <head sha>` nor `clean (…)` for the head sha (**Review** step 3), run **Build** step 3 first |
| `changes-requested` | **Review loop** |
| `ready-to-merge` | **Ship** from step 4. Low-risk and high-risk (agent-queueable) PRs alike: `pr.sh merge` records a high-risk one in the PR body before it queues it. |
| `merge-refused` | Report and stop: `pr.sh merge` refused this commit, so the owner decides. Never run `pr.sh merge` on it again; only a fix pushed with `pr.sh create` (a new commit) makes it `ready-to-merge` again. A refresh merge commit does not: a PR a refresh left with the owner (`Stays with the owner`, **Refresh**) is `merge-refused` too, until a fix and a clean review of it are recorded. |
| `queued` | (Only with `merge: queue`.) Nothing to do: the PR is in the merge queue and GitHub tests and merges it (`WORKFLOW.md §7`). Report it as queued; check `flow.sh status <n>` again later. Never queue it again. |
| `queue-removed` | (Only with `merge: queue`.) GitHub removed the PR from the queue (`flow.sh status` shows the reason). Read the `merge_group` run of its queue branch (`gh run list --event merge_group`). A cause in the PR: a `builder` fixes it (**Build** step 2), a `reviewer` reviews (**Build** step 3), push with `pr.sh create` (a new commit makes the removal stale) and continue with **Ship** from step 2. A cause outside the PR (the failing check also fails on `main` or on other PRs, a flaky test, a stalled or timed-out job; [ADR-025](../../../docs/decisions/ADR-025-requeue-after-a-fix.md)): file a bug for the failing check, or find the open bug that covers it. `scripts/issue.sh create bug --title … --body-file - --label ready-for-agent`, the body with the run ids, the failing test and error, and `## Acceptance criteria`; then `scripts/issue.sh block <n> --by <bug>`. The PR is then `waiting-fix`, and the bug is built first (**Factory** step 4). A commit that was already re-queued after a fix and was removed again, a removal with no fix in code to wait for, or an owner-only (or unknown-risk) PR, which no agent queues: report and stop, the owner decides, and append `queue-removed <head sha>: reported to the owner` to the notes file, with the PR's current head commit as `gh pr view <pr> --json headRefOid` gives it (at least its first 7 characters), so `flow.sh idle` doesn't start a full run for it again; a new commit makes the line stale. Never queue the same commit again yourself, except with `pr.sh merge <pr> --after <bug>` (`requeue`). |
| `waiting-fix` | Only for a low- or high-risk PR the merge gate has not refused on its head commit. Nothing to do on the PR: it waits for the bug that blocks its issue (`flow.sh status` names it), which is ready work of its own and is built first. Report it as waiting; check `flow.sh status <n>` again later. |
| `requeue` | Only for a low- or high-risk PR the merge gate has not refused on its head commit (a refused one is `merge-refused`). The bug that blocks the issue was closed as completed after the queue removed the PR. Run `scripts/pr.sh merge <pr> --after <bug>` (the `Next` line has both numbers): it checks the whole merge gate and the `--after` conditions, records `re-queued … after #<bug> fixed the check that removed it` in the PR body, and queues the **same** commit once more. No push and no merge of `main`: the queue tests it on the latest `main`, which has the fix. Once per commit; when it refuses, it records the refusal: report it and stop. Then as for `queued`. |
| `in-review`, `approved` | Report and stop: owner-only (or risk unknown), so the owner reviews and adds it to the merge queue (with `merge: direct`, merges it on GitHub). A high-risk PR that an agent may queue is `ready-to-merge`, not `in-review`. |
| `merged` | `scripts/flow.sh finish <n>` from the main checkout, then continue with what it reports for the spec. GitHub merged it, after the queue if it was queued. For a spec's own branch `finish` only cleans up and leaves the spec open (it closes through its tickets). When `scripts/pipeline.sh get review` says `split` and the issue has a parent spec (`flow.sh status` showed `Parent: #<spec>`), run the **Spec review** of the PR that merged it right after `finish`. |
| `spec-review` | Only with `review: split`: every ticket of the spec is closed, but no clean final spec review is recorded that covers its last merged PR (its squash commit is in the reviewed SHA). Run the final **Spec review** on it. Bug tickets it files reopen the spec (`building`); a clean final review makes it `complete`. |
| `complete` | Check `FEATURES.md` says `IMPLEMENTED` on `main`, then close the spec with `scripts/issue.sh close <n>`. |
| `abandoned` | Ask the user; act only when they decide. |
| `blocked`, `taken` | Say why and propose something from `scripts/flow.sh next`. |
| `human` | Help without code: research (`.agents/skills/research/SKILL.md`), questions for the owner, a prototype. |
| `done` | Nothing to do. |

## Shape

New work. Keep these steps in this conversation; don't delegate or compact between them.

0. **Design first, where design matters**: a new screen or flow, a visible change to one, or a product question a screen makes concrete. Settle it with the owner in the clickable prototype and record it in `docs/design/prototype-v2/DECISIONS.md`; the spec then names the prototype screens it implements. Skip it for work without a screen and for small changes that follow an existing pattern (`DESIGN.md`).
1. **Grill**: `.agents/skills/grill-with-docs/SKILL.md`. It updates `GLOSSARY.md` and proposes ADRs as decisions settle.
2. **Spec**: `.agents/skills/to-spec/SKILL.md` → a spec issue, following `docs/agents/issue-tracker.md` (`[F0xx]` title, ACs in NL/EN, Test plan, platforms, languages). A spec that touches auth, tenant data, health notes or money (billing, payments, while payments run in the payment provider's test mode) gets the `owner-merge` label when you create it (`scripts/issue.sh create spec … --label owner-merge`): its PRs are recorded as high-risk and agents may queue them. A spec that touches legal or the agents' own rules (the core guardrails) gets `owner-only` instead (`--label owner-only`): every PR of it goes to the owner. Once `@agent-queue billing` is gone from `scripts/high-risk-paths.txt` (payments can move real money), money specs get `owner-only` again. High-risk paths match those areas only by name until their code exists. The owner reviews it and approves it with the `spec-approved` label. Report and stop here; continue with step 3 only once the spec is approved (`flow.sh status` no longer says `needs-approval`).
3. **Tickets**: `.agents/skills/to-tickets/SKILL.md` → sub-issues with blocking edges via `scripts/issue.sh create ticket --parent <spec> [--blocked-by <n>]...`, each with an `## Acceptance criteria` checklist. Size each to merge within a day or two. A spec that waits on another spec is cut too (`needs-tickets`): each ticket is blocked by the other spec's tickets it needs, or by that spec itself (`docs/agents/issue-tracker.md`, **Fivvi rules for tickets**).
4. **Build** the ready tickets unless the user wants to stop.

## Build

Per platform slice of a spec (ADR-033, below) or per ticket; run independent slices and tickets in parallel, as many as `scripts/pipeline.sh get builders` allows ([ADR-035](../../../docs/decisions/ADR-035-lean-pipeline.md); read it before every start, it is the owner's setting). With `builders: 1` start no second ticket or slice while one is in flight, from `flow.sh start` until its PR is merged: wait for the PR in review, CI or the merge queue (`pr.sh wait`, `flow.sh status`) and start the next one on the `main` that has it; a PR that waits on the owner (owner-only, `merge-refused`, `ready-for-human`) does not hold the next one back, and neither spec reviews nor the `reviewer` count (`docs/agents/build.md`, **Parallel builders**). With more than 1, run at most that many builders at once while the 1-minute load (`uptime`) stays under about 50 ([ADR-033](../../../docs/decisions/ADR-033-go-live-mode.md)); count only builders actually running, not PRs that wait on CI or the owner. `flow.sh start` enforces a limit on tickets in progress only when the session sets `FIVVI_MAX_TICKETS`. Start no more agents at once than the tool's rate limits allow, and build tickets that change the same files one after the other.

1. `scripts/flow.sh start <n>` claims it and creates its worktree and notes; it prints the worktree, notes path, `E2E_PORT` and a `Hint` (what this PR changes in `FEATURES.md`, if anything). **For the ready tickets of a spec, start a platform slice instead** ([ADR-033](../../../docs/decisions/ADR-033-go-live-mode.md)): `scripts/flow.sh start --slice <spec> <platform>` (platform `backend`, `web`, `ios` or `android`, read from the ticket titles and labels) claims up to 5 open, unblocked tickets of that spec on that platform, plus one blocked only inside the slice, and makes one worktree, branch and notes file for all of them; it prints the slice (`Slice: #a #b …`) and a `Hint (#n)` for each ticket. One builder builds the whole slice, one reviewer reviews it, and one PR closes every ticket (`pr.sh create` adds the `Closes`, and warns above about 1,500 changed lines: then leave the last tickets for another slice). A ticket the builder reports as not built (blocked, or the rest above the line limit) is taken out of the slice before `pr.sh create`: `scripts/flow.sh slice <first> --drop <ticket>` removes it from `.work/<first>/slice` and unassigns it, so the PR does not close it, `finish` leaves it open and a new slice can take it (the first ticket, which names the branch, can't be dropped). `flow.sh status`, `next` and `finish` work with any ticket of the slice. Use `flow.sh start <n>` alone for a bug, a ticket that names no platform and a spec with one ready ticket on a platform.
2. A fresh `builder` subagent runs `.agents/skills/implement/SKILL.md` on the ticket, following `docs/agents/build.md`, with the issue number, worktree, notes path and hint. It builds test-first with `tdd` and commits; it does **not** review its own work. On `blocked`, stop this ticket and ask the user; when only the owner can answer and they aren't here (**Factory**), `triage` it to `needs-info`.
3. **Review**: a fresh `reviewer` subagent runs `.agents/skills/code-review/SKILL.md` on the head commit, on the axes `scripts/pipeline.sh get review` and the PR's risk ask for, following `docs/agents/build.md` (**Review by risk**): with `per-pr`, both axes (standards and spec) on every PR; with `split`, the standards axis only plus the acceptance-criterion → test check for a `low`-risk PR, and both axes for a `high` or `owner` PR. The risk needs a PR, so with `split` open the draft first (**Ship** step 1) and read `scripts/risk.sh <pr>` before the first review; name the axes in the brief. The reviewer's brief follows `docs/agents/build.md`, with the issue number, worktree, notes path and the scope (`docs/agents/build.md`, **Review**): `full` for the first review; for every later one (a fix, a CI repair, a merge of `origin/main`), `since <sha>` of the last review with its must-fix and should-fix findings. Record each verdict in the notes file as `reviewed <sha> (<scope>): clean` or `not clean`, with `split` naming the axes the verdict covered, `clean (standards)` or `clean (standards, spec)`; the next scope starts there. A low-risk review with no must-fix finding left is recorded as `reviewed <sha> (<scope>): clean (low risk, <n> should-fix follow-ups)`, with `split` and `; standards` before the closing parenthesis. It reports its findings and the verdict `clean on <sha> (standards)`, `clean on <sha> (standards, spec)` or `not clean on <sha>`. For must-fix and should-fix findings, start a fresh `builder` with the findings in its brief (**Build** step 2), then a `reviewer` on the new head commit. At most two fix rounds; the review after the second is review-only: fix nothing, list what's left in the notes file. Note each round in the notes file. Only a `reviewer` verdict can make a review clean. **Review by risk** (ADR-033 item 5, until pilot setup; `docs/agents/build.md`): when `scripts/risk.sh <pr>` says `low` (it needs a PR, so until there is one the risk is unknown and the full rule applies: while a review has must-fix findings, fix them as usual, and a fix round spent before the draft counts as the low-risk one; once a review has no must-fix finding left and there is no PR yet, open the draft with `pr.sh create`, **Ship** step 1, and read the risk), only must-fix findings go to a fix round and there is at most **one**; the should-fix findings still open go to the notes file as follow-ups, and a review with no must-fix finding left counts as clean, recorded as above (**Ship** step 2). A `high` or `owner` PR keeps the rule above. The rule ends at pilot setup.
4. **Ship**.

## Ship

Run `pr.sh` inside the worktree: `cd <worktree> && scripts/pr.sh …`.

1. `pr.sh create --body-file -` with a body shaped by `.agents/skills/pr/SKILL.md`. It runs `scripts/check.sh --fast` (`--full` runs everything), pushes, opens a draft titled after the issue and adds `Closes #<n>`, or `Refs #<n>` for a spec that closes through its tickets (labelled `spec` or with sub-issues, not built as its own ticket): that spec is closed by `scripts/issue.sh close <n>` once `flow.sh status` says `complete`, never by a PR, and `pr.sh create` refuses a body that closes it. Every later push is a plain `pr.sh create`, without `--body-file`: on an open PR it keeps the body. When the draft was opened to read the risk (**Review** step 3) and the head commit has not changed since, skip this step: the draft is pushed and checked at that commit.
2. If a `reviewer` reported `clean on <sha>` for the pushed head commit: `pr.sh reviewed` records it for the head commit, with `--axes standards` when the verdict says `(standards)` (it refuses that unless the review setting is `split` and the PR is `low`-risk, and the merge gate refuses it too). For a `low`-risk PR whose last review has no must-fix finding but `n` should-fix ones (**Review** step 3, review by risk): `pr.sh reviewed --should-fix <n>` records it with the follow-ups, plus `--axes standards` when the verdict says `(standards)` (without `--axes` the record claims both axes); it refuses a `high` or `owner` PR, and the merge gate refuses such a record for one. Otherwise skip it; the PR will stay for the owner (`ship` stops at `ready`, which names the missing review).
3. `pr.sh ship` runs `wait`, `smoke` and `ready` in order and stops at the first failure with its exit code; it records nothing itself, so step 2 comes first. `ready` refuses unless every CI check passed on the head commit and the clean review and the smoke are recorded for it. At the end it prints the step durations of the native jobs. Never chain `wait`, `smoke` and `ready` by hand. On exit 0 the PR is ready for review: note it in the notes file. Otherwise read the step that failed:
   - `wait` exit 1, a check failed: a `mechanic` digs the failing log out and reports the failing step and first error, a fresh `builder` fixes it (**Build** step 2), a `reviewer` reviews the new head commit (**Build** step 3), and push with `pr.sh create` (back to step 2). Exit 2, still running after the timeout (20 minutes, 155 when iOS or Android run): report and stop.
   - `smoke` fails: the preview is not healthy, or Railway did not deploy it and the `railway` CLI is missing or logged out. With the CLI, smoke redeploys a skipped preview itself, in the PR's own environment only; without it, a preview that deployed is still health-checked. Report and stop.
   - `ready` refuses: it names what is missing. Record or fix that and run `pr.sh ship` again; a PR left without a clean review stays a draft for the owner.
4. **Merge.** `scripts/flow.sh status <n>`. On `ready-to-merge`, run `pr.sh merge`: with `merge: direct` (`scripts/pipeline.sh get merge`, ADR-035) it checks the same whole merge gate and then squash-merges the PR itself (`gh pr merge --squash --match-head-commit`, no queue): the PR is merged when it says so, and `scripts/flow.sh finish <n>` follows at once. The ruleset then requires the branch to be up to date with `main`: when GitHub refuses because the PR is behind `main`, `pr.sh merge` says so; do the **Refresh** steps (merge `origin/main`, `scripts/check.sh --fast`, the review of the merge, `pr.sh create`, `reviewed` and `ship` for the new head commit, wait for CI with `pr.sh wait`), then `pr.sh merge` again. With `merge: queue` it checks the merge gate and adds the PR to the merge queue only when every condition holds, then records the queued commit on the PR (for a high-risk PR it first records `**High-risk agent merge:**` with the commit and the reasons). With the queue, being behind `main` is no reason to wait or to merge `main` in: the queue tests the PR on the latest `main`. Once it says "added to the merge queue", report the PR as queued and move on: GitHub squash-merges it when the checks pass on the combined commit (`WORKFLOW.md §7`). Later `flow.sh status <n>` says `merged` (then `scripts/flow.sh finish <n>` from the main checkout, and continue with what it reports), still `queued` (nothing to do), or `queue-removed` (see the playbook). Never run `gh pr merge` yourself, and never use `--auto` or `--admin`. When the gate refuses, it records the refusal and its reasons on the PR for the head commit: report it to the owner and stop, and never retry the merge. The PR stays for the owner (`merge-refused`, under "Waiting on the owner" in `flow.sh next`) until the owner decides or a fix is pushed. Same when the phase is `in-review` (owner-only, or risk unknown).

## Refresh

A `Refresh PR #n (conflicting with main)` line under "Ready for an agent" is a PR GitHub marks as conflicting (#1274): any risk, drafts and owner-only PRs included. Merging `main` into it is ready work, before new tickets (**Factory** step 4); an owner-only PR that waits for the owner is refreshed too, so it never goes stale. `flow.sh status <issue>` shows the same for that PR's issue. A PR parked (its issue or a ticket it closes is `ready-for-human`, or its spec is not approved), in the merge queue, or worked on by a builder (its issue's notes or worktree changed in the last 30 minutes) is not listed. One refresh per PR and run, counted by the run's lock: with no lock (`flow.sh refresh` prints run `-`) there is no one-refresh limit and a PR that still conflicts is listed again by the next `flow.sh next`, so take the lock first (**Factory** step 0).

1. `scripts/flow.sh refresh <pr>`, from the main checkout: it records the attempt for this run and prints the branch, the PR's head commit (the **previous head**, the scope of the review) and the worktree, then `Last review: …` (the last `reviewed <sha> (<scope>): …` verdict in the issue's notes) and `Stays with the owner: …` for every PR whose last verdict is not a clean one for that head commit (not clean, a clean verdict of an older commit, no verdict at all, or a refusal of the merge gate on the head commit). It also writes `refresh-held <previous head>: <why>` to the issue's notes (a PR with no issue has no notes: report it), which keeps the PR `merge-refused` after the push until a `reviewed <sha> (…): clean` line follows it for the PR's then current head (not for the held commit or an older one). When there is none, `scripts/wt.sh add <branch>` recreates it from the branch.
2. In the worktree: `git fetch origin`, then `git merge origin/main`. A merge, never a rebase and never a force-push. A clean merge goes on to step 3. With conflicts: a `mechanic` resolves those that are only unions of both sides (both sides' lines kept, such as two entries appended to the same list); a `builder` (**Build** step 2, with the conflicted files in its brief) resolves any other. Never merge a generated file by hand: resolve its sources, then regenerate it with its generator and let the drift checks prove it. When the conflict needs a product decision, or the builder can't resolve it: `git merge --abort`, `scripts/flow.sh refresh <pr> --owner "<why>"` and leave the PR; it then waits under "Waiting on the owner" with that reason until its head commit changes.
3. `scripts/check.sh --fast` in the worktree (with `ci: full` the same step; `docs/agents/build.md`, **Build**). Fix a failure with a `builder`.
4. A `reviewer` on the merge (**Build** step 3), scope `since <the previous head>`, the merge reviewed by its conflict resolution: what the resolution kept, dropped or merged, not the unchanged code of `main` that came in. The axes follow the review setting and the PR's risk (`docs/agents/build.md`, **Review by risk**); an owner-only or high-risk PR gets both. Carry the open must-fix and should-fix findings of the last review from the notes file (the `Last review:` line says which review) into the brief, as for any later review (`since`, **Build** step 3), so they are not lost behind the merge. Record the verdict in the notes file (or, for a PR without an issue, report it): `reviewed <sha> (since <previous head>): clean|not clean`, or, when step 1 printed `Stays with the owner`, `refresh-reviewed <sha> (merge of main): clean|not clean`, which is not a review of the PR.
5. `scripts/pr.sh create` pushes the merge commit. When `flow.sh refresh` printed `Stays with the owner`, run `scripts/pr.sh refreshed` and stop: the review of the merge sees only the resolution, so it is not recorded clean (no `pr.sh reviewed`), and the PR is not shipped or queued (no `pr.sh ship`, no `pr.sh merge`); it stays with the owner (**Waiting on the owner**, phase `merge-refused`: the push of the merge commit does not clear the hold or a refusal), with its open findings or refusal, and the run's report says so. Otherwise `scripts/pr.sh refreshed` records `🔄 **Refreshed:** merged main at <sha>` in the PR body (a script writes it, never by hand), `scripts/pr.sh reviewed` records the clean verdict for the new head, and `scripts/pr.sh ship` (**Ship** step 3). On a PR that was a draft only to wait for the owner, `ship` stops at `ready` as usual.
6. `scripts/flow.sh status <issue>` or `flow.sh next`: GitHub should no longer call it conflicting (it may need a moment: an `UNKNOWN` state is read again). An owner-only PR is **never queued**: it waits under "Waiting on the owner" again (`Merge PR #n`); a low-risk or high-risk PR goes on as the playbook says (`ready-to-merge`), except one that stays with the owner (step 5).

A PR that still conflicts after this one refresh, in the same run, is not refreshed again: `flow.sh next` lists it under "Waiting on the owner" (`still conflicting with main after a refresh in this run`) and the next run tries once more. Same for a refresh that needs the owner (step 2). Report both in the run's report (**Factory** step 5).

## Spec review

Only with `scripts/pipeline.sh get review` = `split` (ADR-034; with `per-pr` the spec axis ran on every PR and there is nothing to do here). The spec axis runs once per merged slice or ticket PR, and once for the whole spec. `docs/agents/build.md`, **Spec review**, has the details.

1. **Slice or ticket PR** (phase `merged`, after `flow.sh finish`, for an issue with a parent spec): read the PR's number and squash commit from `scripts/spec-review.sh map <spec> --json` (the `pr` of the ticket you just finished; a slice PR shows on each of its tickets). Fetch `origin/main` and note its SHA (`git rev-parse origin/main`): it goes in the brief, and the reviewer reviews that commit. **Final** (phase `spec-review`): the whole spec.
2. A fresh `reviewer` subagent, briefed with the spec number, the PR and its commit (or `final`), the SHA of `origin/main` to review and `scripts/spec-review.sh map <spec>`, reports each acceptance criterion as passing or failing, with file, line, commit and ticket for a failure, and the verdict `clean` or `not clean`. It records and files nothing.
3. For each failing criterion file a bug under the spec: `scripts/issue.sh create bug --parent <spec> --label ready-for-agent --title … --body-file -`, the body naming the acceptance criterion, file, line, commit, PR and ticket it traces to, and with its own `## Acceptance criteria`. Check `gh issue list` for an open bug of the same criterion first.
4. Record the verdict: `scripts/spec-review.sh record <spec> (--slice <pr> | --final) clean|not-clean [--findings <n>] --sha <sha>`, with the SHA of `origin/main` from step 1 (the commit the reviewer reviewed, not the `origin/main` of now). Then `scripts/flow.sh status <spec>`: open bugs make it `building` again, and the bugs are ready work (**Build**). When the final review is clean the phase is `complete`.

## Review loop

1. `pr.sh status` and `pr.sh threads` in the worktree.
2. A fresh `builder` runs `implement` on the failing checks and threads (**Build** step 2), with the thread ids and text in its brief; a `reviewer` then reviews the new commit (**Build** step 3).
3. Push with `pr.sh create` (**Ship** step 1), then reply to each thread: `pr.sh reply <thread> --body "<what changed>" --resolve` when fixed; without `--resolve` when you disagree, so the owner decides.
4. The push made the review and smoke records stale: continue with **Ship** from step 2.
5. Update the notes file, report.

## Factory

The owner says "run the factory", or the scheduled task starts it (every 2 hours on the owner's Mac): work through everything that doesn't need the owner, then report what does. One run at a time.

0. `scripts/flow.sh lock acquire` first, from the main checkout. When it fails because another run holds the lock, report the lock's age as it printed it and stop: claim nothing, start nothing, and don't release a lock you did not take. Keep the run id it prints (`run id: …`) and note it in the run's notes. The lock expires 3 hours after it was taken **or last refreshed**, and `acquire` takes an expired lock over by itself, so a live run renews it: `scripts/flow.sh lock refresh <run-id>` after each ticket the run starts, after each `pr.sh` step that waits (`ship`, `wait`) and after each `pr.sh merge` that adds a PR to the merge queue. `refresh` fails when the lock is gone or another run holds it (it took over after this run went quiet for 3 hours): then stop, claim nothing more, report it, and don't release. Then `scripts/clean.sh` (the worktrees of merged and closed PRs, their simulators, stale DerivedData and turbo cache; report what it lists under "Left for you" with the rest of the run, and never remove those by hand), and `scripts/flow.sh idle`: on exit 0 (nothing for an agent) release the lock, report its output (the "Waiting on the owner" list) and stop; on exit 1 carry on with step 1; on any other exit it is an error: release the lock, report the error and stop.
1. `scripts/flow.sh next`.
2. For each `Finish #n` line under "Ready for an agent" (a merged PR whose issue is already closed) run `scripts/flow.sh finish n`, and for each `Clean up <branch>` line `scripts/wt.sh done <branch>`; `clean.sh` normally did that already. For each issue under "Assigned to you", act on its phase with the playbook (resume `in-progress`, ship `draft-pr`, queue `ready-to-merge`, fix `changes-requested`, clean up `merged`). Skip what waits on a human, including `merge-refused`, what waits on GitHub: `queued`, and what waits on a bug: `waiting-fix`. Handle `queue-removed` and `requeue` as the playbook says.
3. For each `Cut #n` line under "Ready for an agent" (an approved spec in `needs-tickets`), cut its tickets (**Shape** step 3), under these two rules of the owner (6 November 2026):
   - **Read the spec's comments first**: `gh issue view <spec> --comments`, because `issue.sh show` prints only the body and specs approved earlier carry design and payment decisions in their comments. Where a comment and the body differ, the newest owner decision wins. A screen that isn't in the prototype (`docs/design/prototype-v2`) stays held and is reported, not designed by the builder.
   - **Screens wait for the Design v2 foundation (#590)**: API and other tickets without a screen continue. Give every ticket with a screen (web, iOS, Android) `--blocked-by 590`, except #590's own tickets. Never remove a block by #590 yourself; it moves to the foundation tickets when #590 is cut. Report the held count in one line, not each ticket.
4. **Build** first a failing deploy of `development` (a `Deploy bug:` or `Build #n first:` line, always the first lines under "Ready for an agent"; `flow.sh` reads the deploy status of `web` on Railway, `docs/agents/tools.md`): for `Deploy bug:` file the bug with `scripts/issue.sh create bug` (the marker `flow.sh` prints in its body, `## Acceptance criteria`, `ready-for-agent`), for `Build #n first:` take that bug, and build it before every other ticket and before anything else in this step. A `FAILED` or `CRASHED` deploy of `production`, and a deploy status `flow.sh` can't read, are status only under "Waiting on the owner": report them, never work. Then the bugs that block a PR the queue removed (`flow.sh status` of the `waiting-fix` issue names them), then an open bug titled `Nightly UI tests failed` (ADR-034; the nightly run of `ci.yml` opens it and it is `ready-for-agent`; with `ci: fast` or `lean` `flow.sh` lists it once, as `Build #n first (nightly): Nightly UI tests failed`, right after the deploy lines under "Ready for an agent", with `full` it is an ordinary ready ticket; its body names the failing suite, and with `lean` an integration bug (tenant scoping, auth, the database) shows up there): right after a failing deploy and before every other ticket. Then each `Refresh PR #n (conflicting with main)` line (**Refresh**; it keeps every open PR mergeable with `main`, owner-only ones too), before any new ticket. Then the other tickets under "Ready for an agent", at most `scripts/pipeline.sh get builders` in flight (**Build**, and `docs/agents/build.md`, **Parallel builders**; mind the tool's rate limits and tickets that change the same files), each through **Ship** to `pr.sh merge`; `flow.sh finish` follows once GitHub has merged the PR. **With `builders: 1`** take one ticket or slice at a time: with `merge: direct` (ADR-035) `pr.sh merge` merges the PR itself, so run `flow.sh finish` once `flow.sh status` says `merged` (before the owner has applied the ruleset, `pr.sh merge` still queues, and it warns) and start the next ticket; with `merge: queue` wait for the merge first (`pr.sh wait`, `flow.sh status`, refreshing the lock), `flow.sh finish` it, run `flow.sh next` again and only then start the next ticket, on the updated `main`; the exception is a PR that waits on the owner (owner-only, `merge-refused`, `ready-for-human`): leave it and go on. **With more than 1** queue the PRs and carry on with the next ticket instead of waiting for the queue, up to that limit; run `flow.sh next` and the `queued` PRs' `flow.sh status` again after each queue, `finish` the ones that are `merged`: it unblocks the next tickets.
   Each `Review spec #n` line under "Ready for an agent" is the final **Spec review** of a spec in phase `spec-review`; run it once the tickets in flight are queued, like any other ready work.
5. Stop when nothing is ready and every open item waits on the owner. Report the "Waiting on the owner" list from `flow.sh next` (it also labels those PRs `owner-queue` or `owner-decide` on GitHub, and clears the labels of PRs that no longer wait; say so in the report, and never set them by hand) and the "For the owner to read" list (the high-risk PRs agents merged in the last 7 days), the answered questions to `triage` together (`Triage #n … (answered)`), the PRs refreshed in this run and the ones that could not be (**Refresh**), the PRs merged and the PRs still queued in this run, the PRs `pr.sh merge` refused with their reasons, the PRs the queue removed (and the bugs filed for them, the PRs re-queued after a fix), the deploy lines of Railway under "Waiting on the owner", any ticket that stopped as `blocked`, the count of tickets held by #590 and the screens held because they aren't in the prototype (step 3). Then measure the run from the main checkout, `node scripts/usage.mjs snapshot --since <the run's start> --label <date>-factory --out .work/usage/<date>-factory.json`, and report the main changes of `node scripts/usage.mjs compare docs/agents/usage/2026-11-18-full-pipeline.json .work/usage/<date>-factory.json` (`docs/agents/build.md`, **Usage**). Last, `scripts/flow.sh lock release <run-id>`, also when the run stops early on an error after it took the lock; a run that crashes leaves the lock to expire 3 hours after its last refresh.

A PR that `pr.sh merge` refused is reported to the owner, not retried: never merge around a refusal or run `pr.sh merge` again on the refused commit. The same goes for a commit the queue removed, with one exception: after a bug that blocks its issue was fixed, `pr.sh merge <pr> --after <bug>` queues it once more (ADR-025; with `merge: direct` there is no queue, so `--after` refuses and nothing is removed); a second removal goes to the owner. Only the owner adds `spec-approved`. Add `owner-merge` only when creating a spec that touches auth, tenant data, health notes or money while payments run in the payment provider's test mode, and `owner-only` only when it touches legal, the agents' own rules, or money once `@agent-queue billing` is gone (**Shape** step 2); never remove either. Questions only the owner can answer go on the issue with `needs-info`, posted by `triage`.

## Subagents

Three agents, defined once in `.agents/agents/` and pinned to a model tier in every tool (`docs/agents/build.md`, **Tiers**). Start each by name, never as the tool's general-purpose subagent, which would run on this conversation's model.

| Agent | Tier | Start it for |
|---|---|---|
| `builder` | mid | **Build** step 2: a ticket, a fix round after a review, failing checks, PR threads |
| `reviewer` | high | **Build** step 3: the `code-review` axes of the setting and the risk on the head commit, review-only rounds, merge-commit reviews (also the one of a **Refresh**); every **Spec review**. The only source of `clean on <sha> (…)` |
| `mechanic` | small | CI-log digging, simple conflicts (unions, also in a **Refresh**), status and doc edits the brief spells out, waiting on `pr.sh wait` |

A subagent starts fresh, with none of this conversation. Brief it with pointers, not pasted content: the issue number, worktree, notes path and hint, and for a fix the findings, failing checks or threads. The agent files say what to read. Expect the short report `build.md` asks for.

- **Claude Code**: the Agent tool with `subagent_type` `builder`, `reviewer` or `mechanic` (`.claude/agents/`, the model from `tiers.json`).
- **Copilot**: the custom agent of that name (`.github/agents/<name>.agent.md`; its `model` field lists the Copilot names). In the CLI, run it as a subagent by name; in VS Code, as a subagent of the main conversation.
- **Codex**: `spawn_agent` with `agent_type` `reviewer` or `mechanic` and `fork_turns: "none"`; the role pins the model, so don't pass `model`. A native role can't change the sandbox and can't commit in a worktree, so start the `builder` (and a `mechanic` that has to commit) with `scripts/codex-agent.sh mid|small <worktree> <prompt-file>`, which grants that worktree's git dir and its own branch, and keeps `commondir`, `gitdir` and `.githooks` read-only; the prompt file starts with "Read and follow `.agents/agents/builder.md`" (the wrapper has no role) and continues with the brief, and the final message is the report. The same wrapper starts any tier when the roles aren't loaded (the repo isn't trusted in `~/.codex/config.toml`). Details in `docs/agents/codex-model-tiers.md`.
- **No subagent support**: do the same steps inline, one ticket per conversation. A review in the conversation that built is not a `reviewer` verdict: run it in a fresh conversation on the high tier, or skip `pr.sh reviewed` so the PR stays for the owner.

Never hand-edit `.claude/agents/`, `.github/agents/` or `.codex/agents/`: change `.agents/agents/` and run `scripts/agents.sh sync` (`scripts/check.sh` fails when they differ).

## Context hygiene

- One ticket per subagent; the `reviewer` runs the `code-review` axes itself (both with `per-pr` and for a `high` or `owner` PR, the standards axis for a `low` PR with `split`, `docs/agents/build.md`, **Review by risk**), without subagents of its own.
- This conversation runs on the standard context window (`.claude/settings.json` pins `opus`, not `opus[1m]`): every turn reads the whole conversation again, so a long one costs more on each step.
- After **Shape**, after each **Factory** pass, or when this conversation gets long, start a new one: `scripts/flow.sh status` and GitHub rebuild the picture.
- Share research through the notes file, not through this conversation. `flow.sh finish` deletes it.

## After a build

When a build went sideways (rework, failed checks, review rounds, a refused merge), suggest `.agents/skills/retro/SKILL.md` before the conversation ends.
